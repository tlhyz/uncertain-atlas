## B. 核心问题

---

## C. 直觉（ELI15）

你要造一辆车。Level 0 只让你明白：车是「把人从 A 安全运到 B 的机器」，不是「四个轮子的时尚」。

你现在还不该选发动机品牌。  
你已经该写一张不会自欺的问题单：

- 运的是人还是货物？
- 能不能中途改目的地？
- 坏一个轮子会不会两辆车各走各的？
- 乘客凭什么相信已经到达？

「不确定」也一样。后量子是材料科学预告（签名算法会换），不是整车设计已经完成。

## D. 正式：现在能写的问题单（还不是答案）

### 必须保留到后面才填的空

| 主题 | 现在的状态 |
|---|---|
| 状态模型 UTXO / Account / Object | 未学 L2，禁止选择 |
| 共识 Nakamoto / BFT / 雪崩 / DAG | 未学 L3–L4，禁止选择 |
| 是否要 EVM | 未学 L5，默认不应抄 |
| 目标 TPS | 假学习禁令，禁止当第一 KPI |
| 自创哈希或签名 | 反模式，永远倾向禁止 |

### 现在就该记下的问题（建议）

1. 「不确定」的第一句用户承诺是不是：**同一笔授权不会被结算两次，并且收款人知道何时可以放货。**
2. 我们是否接受「分区时停机」来换「commit 后不改」？
3. 谁必须能独立验证？全节点、轻钱包、交易所、监管审计员？
4. 签名算法换代时，旧账户如何迁，谁不能成为万能钥匙？
5. `Apply` 是否从第一天就按「两个实现也必须一致」来写规范？
6. 交易生命周期在产品上如何命名，才不会把广播当成最终？
7. 第一版是结算机，还是通用世界计算机？两者的状态大小和攻击面差一个数量级。

**建议（不是事实）：** 第一版走结算机。理由：后量子验签贵、规范更小、更容易做差分测试、更接近 Bitcoin 那种「规则少所以能活很久」的经验。这是建议，Level 3 之后允许你反驳。

## E. 最小案例

错误的项目启动会：

```text
「我们用某热门 BFT + 某热门 VM + 后量子签名，对标最快公链。」
```

Level 0 合格的启动会：

```text
机器：复制状态机，Apply 必须确定。
授权：签名可替换，消息必须域分离。
历史：高度上最终只能有一个被提交块（是否如此待 L4 论证）。
用户：pending / committed / finalized 分开。
验证：至少一种不信任单一 RPC 的路径。
第一版功能：转账 + 明确最终性；智能合约后置。
开放问题：状态模型、验证者集合、轻客户端证明、升级治理。
```

第二段看起来「没选出酷技术」。这正是它合格的原因。

## F. 真实项目给「不确定」的预告（不是现在深挖）

| 对象 | 以后要偷的可能是 | 现在不要偷的 |
|---|---|---|
| Bitcoin | 规则少、变更慢、全节点可验证 | 把 PoW 当唯一正统 |
| CometBFT | 应用/共识分离、锁规则、确定最终性 | 没懂锁就「投票过 2/3」 |
| Ethereum | 多客户端 + 可执行规范的纪律 | 第一版就上通用 EVM |
| Solana/Sui/Aptos | 冲突可见才能并行 | 先抄吞吐数字 |
| Zcash | 链知道什么/不知道什么仍能防双花 | 先上完整隐私池 |
| 任何链 | 失败后的 invariant | 只抄它们活着时的架构图 |

## H. 攻击者视角

如果「不确定」现在就宣布技术栈，攻击者的工作会变简单：专攻你已经锁死、但你还不理解的那一层。

过早锁死升级密钥、过早锁死单一签名算法、过早锁死「永不暂停」，都是送给对方的固定靶。

---

## I. Trade-off

推迟选择，会让你焦虑，也会让旁人觉得「还没开始」。  
过早选择，会让以后每一课都变成「为我们的决定辩护」，而不是「检验决定」。

本 Atlas 明确选择：先理解二十年，再发明。
