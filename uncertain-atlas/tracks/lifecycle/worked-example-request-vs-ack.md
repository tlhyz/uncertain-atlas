# 例：看见付款请求不是已经授权；看见付款报文不是已经回执；看见回执不是已经最终

**层次**：应用 / 规范对象。  
**分类**：事实（对象边界）+ 推断（产品）+ 建议（产品）。  
**来源**：Bitcoin [BIP-70](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki)（Deployed, Applications, Specification）。  
**对应课文**：[L0.7](../../courses/level-00-machine/L00-M07-one-payment-lifecycle.md)、[L3.6](../../courses/level-03-bitcoin/L03-M06-testing-and-culture.md)。  
**不要写进**：Ethereum 行、L5.1、05b、M5.4、L5.4、03 共识。本页是「付款请求 / 付款报文 / 回执是三件事」，不是付款 URI 已经授权，也不是远程取单已经验证。不要另写怎样拼付款请求或怎样验证书链。不要另写 BIP-71 / BIP-72。

## 官方三件事

规范把商家和顾客之间的付款协议写成三件独立的付款事，不是「看见一份商家请求就已经付了、就已经最终」一件事：

1. **看见付款请求 / 看见商家名字 / 看见证书身份 不是已经授权，也不是已经是那条地址，也不是已经付过。**  
   官方写：本页在旧的「复制地址或点一条付款链接」之上，另开一套商家和顾客之间的消息。钱包收到付款请求之后，必须先核商家身份和签名（若身份类型不是「没有」），必须核自己的时间还没过期，然后把商家身份拿给顾客看，问要不要提交付款。看见付款请求，不是已经授权。看见商家常用名，不是已经是链上地址。看见身份类型写成「没有」，不是已经核过商家。
2. **看见付款报文 / 看见里面有签过的交易 不是已经是回执，也不是商家已经收下，也不是已经有确认。**  
   官方写：顾客授权之后，钱包造出并签好能付清请求输出的交易，再广播到对等网。若请求里写了付款网址，还要把付款报文送到那里。商家服务器收到付款报文，必须自己判断这些交易是否满足付款条件；只有满足，才应当再广播。同一份付款请求若收到多份相同的付款报文，必须每份都回。看见付款报文，不是已经是回执。看见里面有签过的交易，不是商家已经收下。看见送到了付款网址，不是已经有确认。
3. **看见回执 / 看见「已收到」那句备忘 / 看见退款输出 不是已经最终，也不是已经确认，也不是已经退过。**  
   官方写：回执是这套协议的最后一条消息，备忘用来告诉顾客现在的状态，例如「已收下、正在处理」。第二份及以后的回执可以改备忘，用来反映当前状态，例如网上已经看见几份确认。付款报文里的退款输出，是给商家在必要时把钱退回去用的，不是已经退过。看见回执，不是已经最终。看见「已收到」，不是已经确认。看见退款输出，不是已经退过。

消息编码、传输头、证书链拼法、体积上限是规范里的取值或做法，本页不抄。

## 官方为什么这样拆

- **付款请求 ≠ 已经授权：** 官方把核身份、核过期、再问顾客写成三步，不是看见请求就已经付。
- **付款报文 ≠ 已经是回执：** 官方把顾客广播、送到付款网址、商家自己判断是否满足写成不同对象。
- **回执 ≠ 已经最终：** 官方把回执备忘写成处理中的状态，还允许后继回执改确认数。

## 和相邻页的边界

| 对象 | 本页 | 那一页 |

| 付款请求 | 不是已经授权 | 不是付款 URI 已经授权（255） |

## 产品
