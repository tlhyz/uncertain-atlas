# 有状态哈希签名卡（RFC 8391 / SP 800-208）

目的 B。不是选型，不是本机实测。  
对照：无状态哈希签见 [`nist-size-card.md`](nist-size-card.md) 的 SLH-DSA（FIPS 205）。

---

## 它是什么（事实）

[RFC 8391](https://www.rfc-editor.org/rfc/rfc8391.html)（2018-05，Informational）规定：

- **WOTS+**：一次签名。  
- **XMSS**：一棵 Merkle 树把最多 `2^h` 个 WOTS+ 公钥压成一个小公钥。  
- **XMSS^MT**：多层树。

RFC §4.1 原文结构：私钥里有一个 **index**，每签一次更新，指向下一片未用过的 WOTS+。签名带 `idx_sig`、WOTS+ 签、认证路径。验证者从叶子走到根，和公钥里的根比较。

RFC §4.1.5 实现铁律：

> An implementation MUST NOT output the signature before the private key is updated.

[NIST SP 800-208](https://csrc.nist.gov/pubs/sp/800/208/final)（2020-10）批准 **LMS / HSS**（RFC 8554）和 **XMSS / XMSS^MT**（RFC 8391）的**部分**参数集，作为对 FIPS 186 的补充。CSRC 项目页写明：这是有状态哈希签名，不是 FIPS 204/205 那轮竞赛的无状态方案。

---

## NIST 自己划的边界（事实，不是贬损）

SP 800-208 开篇与 CSRC 摘要：

1. **不适合通用使用**：安全取决于仔细的状态管理，这往往很难保证。  
2. **更合适的场景**：私钥使用可被高度控制，并且需要在无状态 PQ 标准化完成前过渡。  
3. **轮廓要求**（同文件）：密钥生成与签名应在**不允许导出私钥**的硬件密码模块里做。  
4. **崩溃纪律**（§8 附近）：接受签名请求后，必须先把叶子下标写入非易失存储，**再**导出签名或接受下一笔请求。只写 OS 文件缓存不够：断电会丢掉「已用过」的记录，下一笔可能复用同一 OTS。

两份不同消息、同一 OTS 叶子：攻击者可以伪造（SP 800-208 安全考虑引用的经典结果）。这是**密码学层**的洞，不是「钱包体验不好」。

## 名义体积（RFC 8391 Table 3，不是实测 CPU）

`|Sig|` 是 RFC 表里的签名字节。KeyGen / Sign / Verify 列是对 `F`/`H` 的调用次数（BDS 最坏情况），**不是**本仓库在某台机器上的毫秒。

| 名称 | \|Sig\| | 一钥可签次数 | 角色 |
|---|---|---|---|
| XMSS-SHA2_10_256 | 2500 B | 2^10 = 1024 | REQUIRED |
| XMSS-SHA2_16_256 | 2692 B | 2^16 | REQUIRED |
| XMSS-SHA2_20_256 | 2820 B | 2^20 | REQUIRED；RFC 写的默认「无特殊需求」选项 |
| XMSS-SHA2_10_512 | 9092 B | 2^10 | OPTIONAL |

同 `h`、`n` 的 SHAKE 实例，RFC 说签名字节与上表相同。  
**不是事实：** 「不确定已选用 XMSS-SHA2_20_256。」SP 800-208 批准的子集与 RFC 全表不必相同；引用时写文件名 + 参数名。

## 和无状态哈希签的差别

| | 有状态 XMSS/LMS | 无状态 SLH-DSA（FIPS 205） |
|---|---|---|
| 私钥是否随签变化 | 是，index 前进 | 否 |
| 签两次同一叶子 | 可导致伪造 | 不适用这套失败 |
| 崩溃后漏写状态 | 部署层直接变成密码失败 | 主要是丢钥/重放别的问题 |
| 一地址能签几笔 | `2^h` 用尽即必须换树/换地址 | 不按树高封顶 |
| 投票签 | **建议不要用**：验证者会重启、会双机热备，状态复制本身被 SP 800-208 禁止导出 | 体积税见尺寸卡；仍要先算不变量 16 |

## 链上必须多钉的一颗钉子

密码学假设成立，**协议**仍要拒绝：`(pk, ots_index)` 在 canonical 历史上签过一笔之后，不得再接受同一对上的另一笔不同消息。  
只靠钱包「下次记得 +1」是部署愿望。节点不查重复 index，复用会变成合法授权。

QRL 官方文档把这写成产品句：树高在造地址时选定；默认高 10 ⇒ 1024 个出站 index；入账不消耗 index；节点拒绝重复 OTS index。见过滤器页 [`../../protocols/qrl/README.md`](../../protocols/qrl/README.md)。那是部署实例，不是「不确定已抄 QRL」。

---

## 对「不确定」

**建议（不是事实）：**

1. 第一版用户签优先看**无状态**方案（FIPS 204/205 或以后正式表），把有状态 HBS 留在「能控制签名环境」的窄口（固件、发行、检查点），不要当热钱包默认。  
2. 若某条路径仍用 XMSS/LMS：共识写不变量 17；实现遵守 RFC 的「先更新再输出」；禁止把同一私钥拷到第二台机器。  
3. 验证者投票签不要用有状态方案。热备 = 拷状态 = SP 800-208 明确反对的导出。  
4. 不填 CPU。Table 3 的调用次数不能改写成「我们主网验得动」。
