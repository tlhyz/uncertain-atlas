# 实例：同一片叶子签了两封不同的信

目的 B。不是考试，不给利用构造。  
先修：L1.2、L1.5、[`stateful-hbs.md`](stateful-hbs.md)。

---

## 故事

阿安的 XMSS 钱包树高 10，叶子 0 还没用。他签「付 1 给阿比」，实现算出 σ，**先把 σ 发到了 RPC**，index 写盘被 OS 缓存，此时断电。

重启后钱包仍显示「下一片是 0」。阿安改主意，签「付 1 给阿昌」。两封**不同消息**，同一 `(pk, ots_index=0)`。

- 若节点只验「这棵树的认证路径能走到根」：两笔都过。  
- 密码学：WOTS+ 一次签的安全论证要求一片叶子只用一次。两份不同消息的签，给伪造者材料（SP 800-208 安全考虑）。  
- 部署：断电 + 先输出后落盘，正好踩 RFC 8391「MUST NOT output the signature before the private key is updated」的反面。

**层：** 密码学（复用破坏一次签假设）+ 实现（输出与落盘顺序）+ 协议（有没有把 `(pk, idx)` 当成已花费授权）。

---

## 五层各说什么

| 层 | 对本故事 |
|---|---|
| 密码学 | 同叶子两封不同消息 ⇒ 一次签假设失效 |
| 协议 | 历史里同一 `(pk, idx)` 不得再授权另一笔 |
| 实现 | 先持久化 index，再让 σ 离开进程 |
| 部署 | 文件缓存、热备拷贝、两台机器同一种子都会复用 |
| 经济 | 「还能再转一次」看起来像功能，其实是把授权卖给伪造者 |

---

## 不是同一故事

| 事件 | 差别 |
|---|---|
| 普通双花（同一 UTXO 花两次） | 授权可以是两片不同叶子；坏的是状态模型 |
| 账户 nonce 重用 | 防的是重放同一请求，不是一次签叶子 |
| SLH-DSA 签两笔 | 无状态；没有这片叶子 |
| 验证者热备双签 | 若用 XMSS 投票，热备本身就在拷状态 |

---

## 对「不确定」

结算机若允许有状态用户签：C19 必须红。  
结算机若用有状态方案给验证者投票：先回头读 SP 800-208「不适合通用使用」和「禁止导出私钥」，再谈委员会。
