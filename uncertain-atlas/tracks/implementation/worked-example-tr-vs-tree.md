# 例：看见 tr 没有树不是已经有脚本路径；看见树表达式不是已经是旧脚本套法；看见压缩钥不是已经是 x-only

**层次**：应用 / 规范对象。  
**分类**：事实（对象边界）+ 推断（产品）+ 建议（产品）。  
**来源**：Bitcoin [BIP-386](https://github.com/bitcoin/bips/blob/master/bip-0386.mediawiki)（Deployed, Applications, Informational）。  
**对应课文**：[L1.4](../../courses/level-01-crypto/L01-M04-canonical-encoding.md)、[L3.6](../../courses/level-03-bitcoin/L03-M06-testing-and-culture.md)。  
**不要写进**：Ethereum 行、L5.1、03 共识、M5.4、L5.4。本页是「tr 没有树不是已经有脚本路径 / 压缩钥不是已经是 x-only」，不是派生钥已经是输出钥，也不是钥匙路径已经揭开有没有树。不要另写怎样算标签微调。

## 官方三件事

规范把 `tr` 描述符写成三件独立的结构事，不是「看见 Taproot 描述符就已经有脚本树」一件事：

1. **看见 tr 只有钥 / 看见没有树参数 不是已经有脚本路径，也不是已经和带树那次同一套微调。**  
   官方写：`tr` 只能当顶层表达式。只吃一把钥时，产出没有脚本路径的 P2TR 输出脚本。带上树参数时，才有脚本路径：树变成 341 里的脚本树，算出默克尔根，再和内部钥合成输出钥。看见只写了钥，不是已经有脚本路径。看见带了树，不是已经是「没有脚本路径」那种微调。
2. **看见树表达式 / 看见一对花括号 不是已经是旧脚本套法，也不是已经随便哪一种旧表达式都能进树。**  
   官方写：树表达式可以是这一层允许的脚本表达式，也可以是一对树表达式。本页写成时，旧脚本表达式里只有 `pk` 能进树。后来能进树的是 379 的 Miniscript 片段，以及 387 的 `multi_a` / `sortedmulti_a`。看见一对花括号，不是已经是旧的脚本哈希套法。看见旧表达式，不是已经都能进树。
3. **看见压缩钥 / 看见未压缩钥 不是已经是 x-only，也不是已经允许未压缩。**  
   官方写：`tr` 下面所有钥表达式都必须长出 x-only 公钥。未压缩钥不允许。压缩钥会隐式转成 x-only。从扩展钥派生出来的钥也必须按 x-only 序列化。本页还另开一种只在 `tr` 里用的钥表达式：一串表示 x-only 公钥的十六进制。看见压缩钥，不是已经是 x-only。看见未压缩钥，不是已经是本页。

树写法、微调公式、测试向量、十六进制宽度是规范里的取值或做法，本页不抄。

## 官方为什么这样拆

- **没有树 ≠ 已经有脚本路径：** 官方把只吃钥和再吃一棵树写成两种产出。
- **树表达式 ≠ 已经是旧套法：** 官方把树写成脚本或一对树，并写明当时只有 `pk` 能进树。
- **压缩钥 ≠ 已经是 x-only：** 官方禁止未压缩，并把压缩写成隐式转换。
