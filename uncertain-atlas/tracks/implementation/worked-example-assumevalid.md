## 1. 核心问题

阿比新装了一台「全节点」。同步很快。他以为自己从创世验了每一条脚本。

实际可能发生了三件不同的事：

1. 旧 **checkpoint**：软件**要求**某几个块必须在链上（还曾用来跳过更早的签名）。
2. **assumevalid**：如果某个已知哈希出现在**被选中的那条链**上，就跳过它祖先的脚本/签名；**不**强迫那条链当最佳链。
3. **assumeutxo**：先装一份 UTXO 快照追上尖，背景链再从创世验到快照高度。

三句都叫「检查点」或「加速同步」时，跳过的规则不同。

---

## 2. 直觉（ELI15）

作业本有三百页。老师说：「第 200 页我亲眼看过是对的。前面的竖式你可以先不重算，但应用题规则、页码、总分还是要核对。若出现另一本总分更高的练习册，即使没有我圈过的第 200 页，你也要换那一本，并且把竖式全部重算。」

这是 assumevalid。  
若老师改口：「没有第 200 页的本子一律扔掉」——那是旧 checkpoint。  
若老师直接塞给你一份「第 200 页时的成绩单」，你先用成绩单接着改后面的分，晚上再从第 1 页重算核对手册——那是 assumeutxo。

## 3. 正式对象（官方发行说明 / 设计文档，事实）

### 3.1 旧 checkpoint（0.3.2 / 0.5.0，官方回顾）

[0.14.0 官网说明](https://bitcoincore.org/en/2017/03/08/release-0.14.0/) 回顾：

| 版本 | 官方怎么说 | 它不是 |
|------|------------|--------|
| 0.3.2 | checkpoint 防止 IBD 时被骗去验一条「不是当时已知最佳链」的替代链（反 DoS） | 「开发者指定哪条链永远正确」——官方写明意图一直是只接受软件已经判定有效的链 |
| 0.5.0 | 在最近 checkpoint **之前**跳过签名验证，加快 IBD | 与 0.14 的 assumevalid 同一开关 |

**事实：** 0.3.2 的 checkpoint **要求**被标记的块出现在区块链里。

### 3.2 assumevalid（0.14.0 引入）

发行说明原文形状：

| 对象 | 官方怎么写 | 它不是 |
|------|------------|--------|
| 跳过什么 | IBD 里很大部分时间花在验脚本/签名；若节点**知道**某块的历史有效，可以跳过其**祖先**的脚本检查 | 跳过 PoW、跳过 UTXO 一致性、跳过结构 |
| 不强迫哪条链 | **不像**旧 checkpoint：不强制使用某条链；与它一致的链处理更快；其它链若本来就会被选为最佳，**仍接受** | 「默认哈希 = 共识指定的唯一历史」 |
| 用户可配 | 用户可以改「假定为真」的那块历史；过期软件改设置仍能加快 | 把默认哈希写进共识规范 |
| 默认 | 发行前按当时链调一个默认值；`-assumevalid=0` **关掉**默认，全部验签名 | 把 0.14.0 那个块高/哈希当永恒（每个发行会改） |
| 不在最佳链上 | 提供的（或默认的）assumevalid 块若不在链上：对历史块**验完全部签名** | 同步失败 / 拒绝更重的链 |
| 分叉 | 更重的有效链不含已知 assumevalid 块：仍切到新最佳链，**放弃**那个 assumevalid 块 | 「开发者锁死了分叉选择」 |

**禁止：** 把 0.14 官网里的 IBD 小时数、电费、某次发行的默认哈希抄进本页当永恒事实。

### 3.3 assumeutxo（Core 设计文档，后到的亲戚）

来自 [`doc/design/assumeutxo.md`](https://github.com/bitcoin/bitcoin/blob/master/doc/design/assumeutxo.md) 与 [`doc/assumeutxo.md`](https://github.com/bitcoin/bitcoin/blob/master/doc/assumeutxo.md)：

| 对象 | 文档怎么写 | 它不是 |
|------|------------|--------|
| 跳过什么（暂时） | 装入 UTXO 快照后，有一段链被**暂时假定**有效；用快照链追上网络尖 | assumevalid（那是跳脚本，不是跳 UTXO 重放） |
| 背景验证 | 另有一条 background chainstate **完整验证**被假定有效的那段；背景尖顶到快照基块时，对 UTXO 集合做哈希，必须等于 `CMainParams::m_assumeutxo_data` 里编译进去的值 | 「快照哈希对上就永远不必从创世验」 |
| 快照从哪来 | 用法文档：**目前没有**规范的快照发行源；下载来的快照仍按硬编码哈希检查 | 共识层对象 |
| 两份 chainstate | 快照激活后可同时存在 IBD 链与 snapshot 链，共用同一套 block index | 两条共识规则 |

## 4. 和弱主观 / 轻客户端不要混名

| | 旧 checkpoint | assumevalid | assumeutxo | Ethereum WS |
|--|---------------|-------------|------------|-------------|
| 层 | 实现 + 曾经的反 DoS | 实现 / 部署 | 实现 / 部署 | 协议（周期）+ 部署（检查点从哪来） |
| 强迫某块在链上 | **是**（0.3.2） | **否** | 快照基块哈希须对上编译值 | 对不上路径应退出 |
| 跳过 | 曾跳更早签名 | 祖先的脚本/签名 | 从创世重建 UTXO（背景再补） | 不是跳脚本；是「太旧的验证者集合不可信」 |
| 更重的另一条链 | 旧机制会挡 | 仍可成为最佳 | 仍跟网络尖；背景继续验 | 另一套经济牙 |
| 关掉的办法 | （历史机制） | `-assumevalid=0` | 不 `loadtxoutset` | 从创世跟、或拒绝过期检查点 |

## 5. 攻击者

| 攻击 | 机制 | 官方设计挡的 | 挡不住的 |
|------|------|--------------|----------|
| 把默认哈希当共识 | 文案 | 更重链仍可抛弃 assumevalid | 用户以为「Core 开发者选了唯一历史」 |
| 错误的 assumevalid | 用户/发行设了一个无效历史里的哈希 | 该哈希若不在被选中的链上，会退回全验签名 | 该哈希**在**被选中的链上且祖先脚本其实无效 → 你跳过了本该失败的验 |
| 把 assumeutxo 当永久免验 | 只比快照哈希 | 背景链应对到基块并核 UTXO 哈希 | 用户在背景验完前就把节点当「已从创世验证」 |
| 和 WS 糊成一句 | 「都是检查点」 | — | PoS 换血与跳脚本是两件事 |

## 6. 五层

| 层 | 本页能说的 | 不能说的 |
|----|------------|----------|
| 密码学 | 跳过的是脚本/签名验，不是哈希函数被关掉 | 「有 assumevalid 所以不验 PoW」 |
| 协议 | 这些开关**不是**共识规则本身 | 把默认哈希写进「Bitcoin 规范」 |
| 实现 | `fScriptChecks` 一类门；两份 chainstate | 没读实现就写「都跳过了结构检查」 |
| 部署 | 发行默认、用户 `-assumevalid=0`、快照从哪下载 | 某次发行的哈希、IBD 小时 |
| 经济 | 加速 IBD 降低全节点门槛 | 官网 0.14 的计费实验 |

---

## 7. 对不确定的意义（建议）

- 第一版若从创世复算：默认不要跳脚本。若以后做 IBD 加速，产品句必须写：**跳过哪条规则、是否强迫链、如何关闭、背景是否补验**。
- 不要把 assumevalid / assumeutxo / 弱主观检查点 / 旧 checkpoint 写成一个「检查点」模块。
- 硬编码哈希是发行物，不是共识对象。审查默认值，允许 `=0`。
- 后量子验签更贵，会有人更积极推销跳过。句子必须先写死跳过的是什么。

---

## 8. 禁句

- 「全节点从创世验证了每一条脚本」（未声明是否 assumevalid / assumeutxo）
- 「assumevalid 和旧 checkpoint 一样锁死历史」
- 「assumeutxo 之后不必再从创世验 UTXO」
- 「这就是 Bitcoin 的弱主观性」
- 把 0.14 的 IBD 耗时、某发行默认哈希、未在官方说明出现的「两周埋葬」当本页事实
