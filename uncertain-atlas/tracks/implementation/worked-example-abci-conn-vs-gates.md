## 官方三件事

规范把 ABCI 客户端和服务器写成三件独立的传输事，不是「看见应用已经接上就已经是四门、已经隔离、已经快」一件事：

1. **看见同进程 / 看见编进同一个二进制 不是已经有套接字隔离。**  
   官方写：最简单的实现是用 Go 的函数调用。Go 写的应用可以和 CometBFT 链进同一个二进制。看见同进程，不是已经有套接字边界。看见一个进程，不是已经是另一条传输。看见链在一起，不是已经换了信任对象。
2. **看见语言里有 gRPC / 看见这是最容易的做法 不是已经是高性能路径。**  
   官方写：不用 Go 时，若语言里有 gRPC，这是最容易的做法，但会有显著的性能开销。官方还写：长度前缀方案不适用于 gRPC。看见最容易，不是已经快。看见能回话，不是已经没有开销。看见套接字那套前缀，不是已经套在 gRPC 上。
3. **看见一条 ABCI 连接 / 看见已经能回话 不是已经够用，也不是已经是四门。**  
   官方写：ABCI 服务器必须能处理多条连接，因为 CometBFT 用四条。看见回了一句，不是已经齐了连接。看见四条连接，不是已经是 Prepare / Process / Finalize / Extend 那四门。看见客户端，不是已经只是共识引擎；官方还写测试工具也是一种 ABCI 客户端。

长度前缀做法、protobuf 字段表、ABCI-CLI 命令是规范里的取值或做法，本页不抄。

## 官方为什么这样拆

- **同进程 ≠ 已经隔离：** 官方把函数调用和套接字 / gRPC 分开。
- **gRPC 最容易 ≠ 已经快：** 官方把容易和显著开销分开，也把长度前缀和 gRPC 分开。
- **一条连接 ≠ 已经够用 / ≠ 已经是四门：** 官方把必须能处理多条连接，和四门方法分开。
