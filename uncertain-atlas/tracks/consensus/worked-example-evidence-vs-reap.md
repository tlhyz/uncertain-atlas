# 例：看见先装证据不是已经装满交易；看见两条收交易上限不是已经同一条；看见 MaxBytes 写成 -1 不是已经没有上限

## 官方三件事

规范把造一块提案写成三件独立的共识事，不是「看见先装证据就已经装满交易」一件事：

1. **看见未处理的证据优先于内存池交易 / 看见先装证据 不是已经装满交易，也不是已经执行，也不是已经过了 Process。**  
   官方写：未处理的证据比内存池里未处理的交易优先。看见先装证据，不是这块已经装满交易。看见证据进了提案，不是这些证据已经执行。看见证据占了位置，不是已经过了验收。
2. **看见提案按扣掉头、上次 commit、证据之后的上限收交易 / 看见内存池按假定没有证据的上限收 不是已经同一条上限。**  
   官方写：从内存池收交易时，先扣掉头、整块开销、上次 commit 和证据，再谈还能装多少交易。进池之前的体积检查用同一套扣法，但假定没有证据。看见提案这边的交易上限，不是内存池已经按同一条收。看见内存池收得下，不是提案扣掉证据之后还收得下。
3. **看见 MaxBytes 写成 -1 / 看见把未处理交易全给了 Prepare 不是已经没有上限，也不是应用已经可以随便回。**  
   官方写：若块上限写成 -1，引擎会把内存池里未处理的交易都交给 `PrepareProposal`。应用回的列表仍不得超过这次请求里的 `MaxTxBytes`。看见写成 -1，不是已经没有上限。看见整池都给了应用，不是应用已经可以随便回。看见回了列表，不是已经过了 Process。

扣减公式、整块体积取值、怎样收割是规范里的做法，本页不抄。

## 官方为什么这样拆

- **先装证据 ≠ 已经装满交易：** 官方把证据优先写成装块顺序，不是执行，也不是验收。
- **两条收交易上限 ≠ 已经同一条：** 官方把提案扣掉证据和内存池假定没有证据写成两套上限。
- **MaxBytes 写成 -1 ≠ 已经没有上限：** 官方把「整池都给 Prepare」和「应用仍不得超过 MaxTxBytes」写成两件事。
