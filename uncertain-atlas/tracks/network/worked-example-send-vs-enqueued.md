# 例：看见 HasChannel 为真不是已经入队；看见 Send 回了假不是已经断开；看见 TrySend 回了假不是已经和 Send 同一把尺

**层次**：网络 / 对等发送。  
**分类**：事实（对象边界）+ 推断（产品）+ 建议（产品）。  
**来源**：CometBFT 官方 [API for Reactors](https://github.com/cometbft/cometbft/blob/main/spec/p2p/reactor-api/p2p-api.md)。  
**对应课文**：[L9.1](../../courses/level-09-systems/L09-M01-p2p.md)。  
**不要写进**：Ethereum 行、L5.1、M5.4、L5.4、03 共识图谱、Bitcoin 行。本页是「HasChannel 不是已经入队 / Send 回假不是已经断开 / TrySend 不是已经和 Send 同一把尺」，不是 Broadcast 已经送到，也不是 NumPeers 已经数完。不要另写怎样入队或怎样编 protobuf。

## 官方三件事

规范把往一个人对等节点发消息写成三件独立的网络事，不是「看见能发就已经入队、已经送到、已经知道为什么失败」一件事：

1. **看见 HasChannel 为真 / 看见对端宣布了通道 不是已经入队，也不是已经送到。**  
   官方写：`HasChannel()` 用来测对端实不实现这条通道。若对端没有这条通道，`Send` 和 `TrySend` 都会立刻回假，因为发送一定失败。看见通道在，不是已经入队。看见对端宣布了，不是已经送到。看见辅助方法绿了，不是已经发出去。
2. **看见 Send 回了假 / 看见阻塞过 不是已经断开，也不是已经送到。**  
   官方写：两条发送方法回的是「编好的消息能不能进这条通道的发送队列」。最常见的假，是队列满。另外还会因人对等节点已经停、给了未登记的通道号、或编载荷出错而回假。`Send` 是阻塞的：队列过了一段时间还满，才回假。看见回了假，不是已经知道是哪一种理由。看见阻塞过，不是已经断开。看见方法还在，不是已经送到。
3. **看见 TrySend 回了假 / 看见立刻失败 不是已经停掉这个人，也不是已经和 Send 同一把尺。**  
   官方写：两条发送方法的差别是**什么时候**回假。`TrySend` 不阻塞：队列满就立刻回假。看见立刻失败，不是已经停掉这个人。看见回了假，不是已经和 `Send` 等过同一段时间。看见非阻塞，不是已经送到。

发送超时秒数、通道号、队列容量是规范里的取值或做法，本页不抄。

## 官方为什么这样拆

- **HasChannel ≠ 已经入队：** 官方把「对端有没有这条通道」和「已经进了发送队列」分开。
- **Send 回假 ≠ 已经断开：** 官方把回假的几种理由分开，也把阻塞和已经送到分开。
- **TrySend 回假 ≠ 已经和 Send 同一把尺：** 官方把立刻回假和阻塞后再回假分开。
