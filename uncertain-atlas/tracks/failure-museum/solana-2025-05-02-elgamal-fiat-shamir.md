# 失败案：验绿不是 Fiat-Shamir transcript 已经绑完；Token 程序未改不是证明程序已经可靠

层：**密码 + 协议 + 实现**（链上 ZK ElGamal 证明程序做 Fiat-Shamir 时漏哈希部分代数分量；验绿可放行伪造证明；先前审计与未见利用不是 soundness 已成立）

官方披露：

- Solana 官方复盘：[Post-mortem May 2, 2025](https://solana.com/news/post-mortem-may-2-2025)。无 CVE。本页只采用该页已写出的句子。无已知利用。

**事实（官方原文能对上的句子）：**

- 2025-04-16，研究者经 Anza GitHub Security Advisory 报告潜在漏洞，含概念验证。Anza、Firedancer、Jito 确认：可以构造 **ZK ElGamal Proof 程序会当成合法的任意证明**。无已知利用。
- Token-2022 机密转账走两个程序：Token-2022 管铸币与账户主逻辑；**ZK ElGamal Proof** 是原生程序，验证加密余额与交易是否正确。
- 典型做法：把交互式零知识协议用 **Fiat-Shamir** 变成非交互。Fiat-Shamir 规定证明者用哈希产生公开随机数。**验证时必须哈希组成该证明的全部代数分量**。
- 漏洞：链上该程序生成 Fiat-Shamir transcript 的哈希**漏掉部分代数分量**。复杂攻击者可用这些未哈希分量，伪造未经授权动作的证明并过验。官方：只影响 Token-22 **机密代币**，可导致无限铸币或从任意账户取款。
- 04-17 开始私下给验证者发补丁；当天认定另一处同类问题，发第二份补丁。04-18 超过超级多数质押打上补丁后公开。集群已采纳。资金未受险。
- 补丁在 ZK ElGamal Proof 程序。Token-2022 **不必改**。该程序先前被审计过。官方重复：无已知利用。

本页不写怎样用未哈希分量伪造证明，不抄补丁版本进不确定常量。验绿不是 transcript 已经绑完。

## 1. 发生了什么

机密余额靠一张证明说「我没偷看、也没造钱」。  
把两人对话压成一张纸，靠哈希当裁判的随机数。  
纸上有几项没进哈希。  
裁判仍举绿牌。  
绿牌不是钱没被造出来。  
Token 柜台没改门，不等于验票的人已经看完全部项。  
验绿不是 Fiat-Shamir transcript 已经绑完。

## 2. 根因

Fiat-Shamir 的绑定范围，必须等于验证者事后当成「已承诺」的全部代数分量。漏一项，那一项就可以被改。  
验绿只说明验证函数对这张字节返回真，不说明陈述仍被绑住。  
Token-2022 主逻辑可以完全正确；它信任的证明程序若 transcript 不齐，铸币 / 取款谓词仍破。  
先前审计与「未见利用」是披露方判断，不是数学证明 soundness。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 13 / CVE-2019-7167 | BCTV14 构造可靠性 / 仪式多余元素；本页是 FS transcript 漏项 |
| 不变量 28 | 有效性证明必须点名被锁程序；本页是被锁程序自己漏哈希 |
| 不变量 79 | ICS-23 验绿 ≠ 叶子在原树 |
| 不变量 90 / 91 | Sui 崩溃 / 隔离；不是证明 |
| 本页 | **验绿 ≠ transcript 已绑完全部代数分量；Token 程序未改 ≠ 证明程序已可靠；先前审计 ≠ 这次哈希已齐；未见利用 ≠ Verify 已成立** |

## 3. 被破坏的 invariant

- Fiat-Shamir transcript 必须纳入验证时当已绑定的全部代数分量（不变量 95）
- `Verify = 接受` 不得单独充当「不可铸、不可偷」
- 应用层未改不是证明层已齐
- 审计通过与未见利用，不是 soundness 测试已覆盖漏哈希

## 4. 为什么测试没发现

幸福路径：诚实证明者按规范填全部项，验绿。  
只测「合法机密转账能过」会绿。  
边角要：改未被哈希的分量，陈述变了，验证仍真。  
先前审计可以覆盖电路与实现主路径，仍漏 transcript 集合。官方自己写该程序曾被审计。

## 5. 修复

官方：补 ZK ElGamal Proof 程序；第二处同类再补一刀。超级多数质押采纳后公开。Token-2022 不改。  
私下分发补丁是部署止血，不是谓词已写进规范测试。  
无已知利用不是「从来没有假证明」。

## 6. 「不确定」若同类

1. 第一版结算保持透明可加总的供给。机密余额 / 链上 ZK 证明是第二阶段。
2. 若提供非交互证明：必须列出 transcript 分量清单，并测「漏一项必须红」。验绿不得写成不可通胀。
3. 应用程序与证明程序是两个对象。只补一个、另一个「不必改」，必须写成信任边界，不得写成两边都已齐。
4. 审计与「未见利用」写在披露栏，不写进产品保证。
5. 这和 Sprout 构造可靠性（13）、ICS-23 验绿（79）、有效性点名程序哈希（28）不是同一句。
6. 不要写怎样伪造。不要抄客户端版本。不要把超级多数打补丁抄进不确定法定人数。

## 7. 回归测试

形状（不是利用包）：文案把「证明程序验绿」写成不可铸 / 不可偷必须红。把 Token 程序未改写成证明层已齐必须红。把先前审计 / 未见利用写成 transcript 已绑完必须红。与 CVE-2019-7167 糊成一句必须红。
