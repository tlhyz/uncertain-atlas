# 失败案：2013-03 Bitcoin 意外分叉（BIP 50）

层：**实现**把数据库锁上限变成了未写明的共识规则；**部署/社会**用算力协调选回兼容链。

## 1. 发生了什么

2013 年 3 月，出现一个输入数量比以往更多的块。Bitcoin **0.8** 节点（LevelDB）接受；部分 **0.8 之前**节点（Berkeley DB 锁上限）拒绝。链意外分成两条。  
按 BIP 50：当时与 0.8 不兼容的那条（0.8 链）约有 60% 算力，因此不会自动按「更重链」合拢到旧规则。

## 2. 根因

0.8 换存储引擎时，旧节点 BDB 的锁数量限制从未被当成协议对象写进规则，却能让旧节点拒绝一个「否则合法」的块。  
Testnet 上测过「最大块」，没测到「更小但更吃锁」的块。0.7 还把矿工目标块大小变成可配置，触发窗口被打开。

**事实来源：** [BIP 50](https://github.com/bitcoin/bips/blob/master/bip-0050.mediawiki)（Informational，Gavin Andresen，2013-03-20）。本页不另引新闻里的价格。

## 3. 被破坏的 invariant

- **确定性 / 实现一致：** 同一块，两个实现（两版本）一收一拒。  
- 用户看见的「确认」在两条历史上分叉。

密码学与「最重合法链」规则此时可以仍然成立——两边都认为自己合法。

## 4. 为什么测试没发现

最大块测试 ≠ 最大锁消耗测试。实现细节（DB 锁）没有被提升为共识测试向量。

## 5. 修复

BIP 50 记录：为尽快恢复单一 canonical 历史，BTCGuild、Slush 等把 0.8 降回 0.7，让多数算力站在旧节点也能验证的链上，0.8 节点随后重组。  
随后发 0.8.1 等补丁，把这类隐式限制变成明确、短暂的兼容规则（细节以 BIP 50 正文为准）。

## 6. 「不确定」若同类

1. 存储引擎、锁、内存上限若能让节点拒绝块，必须升级成**显式共识限制**或保证所有实现相同。  
2. 差分测试：新旧版本、两存储后端，同一块必须同裁决。  
3. 换引擎是实现变更，不是「无关重构」。  
4. 社会协调能救命，但它是**部署/治理**，不要写进「协议自动安全」。

## 7. 回归测试

构造：块在「新实现」可接受、在「旧实现资源上限」处失败。期望：要么两实现都拒（显式规则），要么都收。禁止只在一种后端绿。不得 skip。
