# 失败案：槽号当块身份不是同槽两块已经能互修；Turbine 传一次不是故障已全网看见

层：**协议 + 实现**（块与状态用槽号当主键；同槽两份不同块被当成同一对象；分区修不回来；乐观确认不是已经 rooted）

官方披露：

- Solana 官方复盘：[Mainnet Beta Stall - Postmortem](https://solana.com/news/mainnet-beta-stall---postmortem)（2020-12-04）。无 CVE。本页只采用该页已写出的句子。现场直播页不是本页。2021-09 初报与 2022-04-30 同族，不并进本页。2022-09-30 是确认了仍不能当父块，另立。

**事实（官方原文能对上的句子）：**

- 2020-12-04 约 1:46pm UTC，Mainnet Beta **停住新块确认**。协调重启约 6 小时内恢复。多数停机时间花在等足够质押权重回来。官方：资金未受险；去中心化交易所成交因重启未受险。
- 某验证者开了**两台实例**，同一槽传出**多份不同块**，最终形成 **3 个未确认的少数分区**。分区之间下不了对方建议的块。停的是一条**已知**的块传播 / repair 路径：同槽重复块**不能在分区间修复**。官方反事实：若同样分区发生在**两个不同槽**，网络最终能修好并前进；若 leader 只出了一份损坏块，网络能认出来、不纳入共识。
- 活性失败来自 repair / 处理代码里的已知问题；触发方式来自 Turbine **当时未知**的故障传播。Tower **能**处理同槽分叉、不同人投不同叉、缺块、任意到达顺序，只要故障验证者不足 ⅓。这是已知的 Mainnet Beta **数据可用性**问题，可以造成活性失败。
- 跟踪块与该块计算状态的内部结构，用 **PoH 槽号（u64）当身份**。官方写这是错误映射，Mainnet Beta 之前就有，当时正在拆。传出两份不同块的验证者把块送到分区 A 与 B，第三分区检出故障。三个都是少数分区，谁都不够单独共识。intake **无法区分同槽的块 A 与块 B**，拿到 A 或 B 的分区以为对面是同一块。状态转移不同，挂在该槽一块上的后续叉被对方拒。
- Turbine 有高概率在投票前让很多人看见同块的重复 shred，从而丢掉故障块。官方：同类故障曾丢掉大量块。Turbine **不保证**分区出现前故障已传遍。这次失败来自一项优化：每个验证者对**同一槽、同一 shred 下标**，只从**任意一块**传一次。
- 验证者在某槽之后不再生成 root；最后乐观确认在更后的槽。中间 32 块没有转账，只有投票与确定性的空市场 crank。社区选择以 **rooted 槽**为硬分叉点重启，丢掉乐观确认段。官方：那三段分区当时**没有被 Tower rooted 或乐观确认**，没有最终任何交易。若中间有转账 / 成交，会连乐观块一起恢复；这次选择避免不必要的运维风险。

本页不写怎样让两台实例走出三分区，不抄槽号 / 验证者人数 / 官网交易量进不确定常量。不要把官网吞吐当事实。槽号当块身份，不是同槽两块已经能互修。

## 1. 发生了什么

同一槽，两份不同的块，送到三间屋子。  
屋子用门牌号认块，不认指纹。  
你以为对面拿的是同一本，其实页码一样、字不一样。  
修洞的人按门牌要块，永远要错。  
票可以处理同槽两份叉；仓库认不出两份货。  
乐观确认了，也不等于已经钉在地上。  
槽号当块身份，不是同槽两块已经能互修。

## 2. 根因

块与该块算出的状态，用槽号当主键。同槽两份不同哈希，被当成同一对象。  
repair 按槽号要块，拿到 A 的人以为 B 那边已经有「这块」。状态对不上，后续叉互拒。  
Turbine 对同一 (槽, shred 下标) 只传一次，故障 shred 不一定先到齐。传播成功概率不是 DA 已成立。  
Tower 能容忍同槽分叉，不是 intake / repair / bankforks 已经按哈希跟踪。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 86 / 2022-09-30 | 确认了正确版本仍不能当父块；本页是同槽两块连互修都做不到 |
| 不变量 87 / 2023-02-25 | 恢复 shred 缺父槽字段；本页是块身份用槽号 |
| 不变量 12 | 同根不同列表 |
| 不变量 36 | 宣布 ≠ 已收到 |
| 不变量 89 / 2022-04-30 | 入站洪水 ≠ 停链 |
| 本页 | **槽号当块身份 ≠ 同槽两块已可区分；repair 按槽要块 ≠ 分区间能互修；Turbine 传一次 ≠ 故障已全网看见；Tower 能处理同槽分叉 ≠ DA 已齐；乐观确认 ≠ 已经 rooted / 重启必保留** |

## 3. 被破坏的 invariant

- 块与该块状态必须用内容哈希当身份，不得只用槽号 / 高度当主键（不变量 94）
- 同槽两份不同块必须能像不同槽的分叉一样被 repair / 重放
- Turbine 丢弃「已传过的 (槽, 下标)」不是故障已传播
- 乐观确认不是已经 rooted，也不是重启必保留

## 4. 为什么测试没发现

幸福路径：一个槽一份块，或损坏块在投票前被丢掉。  
只测「Tower 能处理同槽分叉」会绿——共识算法那句可以仍真。  
边角要：两份不同块已经进了不同少数分区，intake 仍按槽号认同一对象。  
官方写：若落在两个不同槽，repair 最终能走通。测试若只换槽号、不换「同槽两哈希」，会绿。

## 5. 修复

官方分阶段：Turbine 更早探故障（不完整）；流言传第一份故障（不完整）；repair / replay / blocktree / bankforks **按哈希而不是槽号**跟踪（完整修复）。另做含乐观块的重启演习。  
1.4 已带第一阶段。完整重构要一个发布周期。  
重启选 rooted 槽当硬分叉点，丢掉乐观段——那是这次运维选择，不是乐观已经等于最终。

## 6. 「不确定」若同类

1. 块、银行、repair 主键必须是内容哈希。高度 / 槽号只当索引，不当身份。
2. 同高两份不同块必须能互修、能分叉选择。按高度要块，对面说「我有这块」不算。
3. 传播协议的「传一次」优化必须点名按哪个身份去重。按高度去重会把第二份合法分叉当已经传过。
4. 乐观确认必须写成未 rooted。产品句不得把乐观当结算。重启演练必须覆盖「保留乐观」与「丢掉乐观」两条，且丢掉必须点名没有用户资金转移。
5. 第一版不要抄官网吞吐，也不要把「丢过很多故障块」写成 DA 已保证。
6. 这和确认了不能当父块（86）、恢复 shred（87）、同根不同列表（12）、入站洪水（89）不是同一句。
7. 不要抄槽号 / ⅓ / 官网交易量。不要写怎样把两台实例配成三分区。

## 7. 回归测试

形状（不是利用包）：文案把槽号 / 高度写成块身份必须红。把同槽两份不同块写成已经能互修必须红。把 Turbine「传一次」写成故障已全网看见必须红。把乐观确认写成已经 rooted / 重启必保留必须红。与 2022-09-30 糊成一句必须红。
