# 失败案：ASA-2023-002 默认块上限不是第一轮活性 SLA

层：**部署 + 协议**（`BlockParams.MaxBytes` 默认值；不是一条新的块规则漏洞）

官方披露：[ASA-2023-002 / GHSA-hq58-p9mv-338c](https://github.com/cometbft/cometbft/security/advisories/GHSA-hq58-p9mv-338c)。咨询标 **Low**。受影响：All。本页不另编 CVE——咨询未给 CVE ID。官方写：这**不是**会直接丢资金的可利用漏洞；可能按网络地形轻微影响出块延迟。

**事实（官方原文能对上的句子）：**

- 默认 `BlockParams.MaxBytes` 对常见用例**偏大**，被用满时可能影响出块时间和共识参与。
- 链必须按自己的用例设这个共识参数。应评估「提案块顶到上限」时的带宽与块延迟。
- `timeout_propose` **应当用最大允许块大小当参照来算**。
- 上限设大的两条含义：传播一块要更多带宽；传播一块要更高延迟。合在一起可能让第一轮参与变少，有时要再开一轮才能过门槛，并按地形与环境导致超时。
- 咨询点名环境因素：验证者人数、地理分布、连通（延迟 / 带宽 / 可达）、交易模块逻辑等。
- 官方建议：若「第一轮就凑齐」对你重要，把该参数调到更小。
- 团队复查后确认：超过应用设定 `MaxBytes` 的提案块**不会被节点接受**。仍决定加更早的健全性检查（#1408）。
- 文档更新：#1405。有时改 `BlockParams` 要网络升级。

本页不把咨询里的示例块大小抄进不确定常量。证据池的 `MaxBytes`（防刷证据）是另一对象，见证据精读。

## 1. 发生了什么

链把仓库默认块上限原样上主网，以为「规范默认 = 第一轮总能过」。  
官方说：默认对常见用例偏大。顶满时传播变慢，第一轮可能凑不齐，再开一轮，甚至超时。钱没被偷，活性先坏。

## 2. 根因

共识参数默认被当成已经按地形算过的 SLA。  
`MaxBytes` 是上限，不是「这个大小一定能在 `timeout_propose` 里传完」。  
超时秒数若按小块调、上限按大块留，两套默认会打架。

这不是：

| 案 | 对象 |
|----|------|
| ASA-2024-004 / 不变量 46 | 默认证据窗可能短于解绑 |
| 不变量 47 | 本地 `timeout_commit` 不是最终性 |
| 不变量 48 | 最大序列化长度不是接收分配 |
| 不变量 52 | 应用回的 post-commit 等待 |
| 证据精读的 MaxBytes | 块里证据体积封顶，防刷证据 |
| 本页 | **默认块上限 ≠ 第一轮活性** |

## 3. 被破坏的 invariant

- 块大小上限必须按传播与第一轮参与重算；仓库默认 `MaxBytes` 不是活性 SLA（不变量 63）
- `timeout_propose` 必须对照该上限
- 超限块必须拒（官方已确认；更早检查是实现加固）

## 4. 为什么测试没发现

幸福路径：块远小于上限，或验证者同机房。  
只测「超限必拒」会绿，看不见「顶满上限时第一轮凑不齐」。  
短测网的延迟不是主网地形。

## 5. 修复

- 无代码补丁当「默认已变安全」。处置是改文档、让链自己设参数；另加更早的超限检查。
- 官方：有时要网络升级才能改 `BlockParams`。

改文档 ≠ 默认已经适合你的验证者分布。

## 6. 「不确定」若同类

1. 第一版必须自己写 `MaxBytes`，并写清第一轮参与是否是产品要求。不要把仓库默认当 SLA。
2. `timeout_propose`（本地）必须对照该上限来选；不要抄文档秒数。
3. 超限必须拒。这是共识参数，不是接收分配（48），也不是证据体积（另一条 MaxBytes）。
4. 不要抄咨询里的示例兆字节。
5. 后量子票更大时，更要把「顶满一块」的传播算进超时，而不是先抄默认再希望第一轮过。

## 7. 回归测试

形状（不是利用包）：文案把默认 `MaxBytes` 写成「第一轮总能过」必须红。超限提案必须拒。`timeout_propose` 文档若不提块上限必须红。只测局域网小块不得标「默认已安全」。
