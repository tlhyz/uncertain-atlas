# 失败案：2023-05 出站待宣布集合排序卡住 P2P

层：**实现 + 网络 + 部署**（每对等节点的出站库存集合；2023 年 5 月上旬被真实网络活动触发）

无 CVE 号。来源：[Bitcoin Core 官方披露](https://bitcoincore.org/en/2024/10/08/disclose-large-inv-to-send/)。**Medium**。修复随 **v25.0**（2023-05-25）。

## 1. 发生了什么

v25.0 之前，每对等节点的 `m_tx_inventory_to_send`（准备向对方宣布的交易集合）可以长到：构造 INV 时按依赖和费率**排序**的时间，妨碍与所有对等节点通信。2023 年 5 月上旬的网络状况触发了这次 DoS，影响块和交易传播，以及连接保活。

本页不抄旧实现的固定排空速率当不确定常数，不写如何养肥集合。

## 2. 根因

出站待宣布集合的增长可以快过排空。排序在 P2P 线程上做。只听不宣布的对等节点（公告称 spy nodes）自己不报交易，集合里仍堆着它们其实已经知道的交易，排序更久。观测：排序几乎吃掉 P2P 线程的全部时间。

这不是 52915（入站 INV 灌发送缓冲）、不是 52920（入站 GETDATA 单连接空转）、不是 52922（宣布块后不交付）。

## 3. 被破坏的 invariant

- 库存三个方向必须各自有配额：出站待宣布不得大到排序卡住所有人（不变量 45）
- 只听不讲的对等节点是合法拓扑，必须算进配额

## 4. 为什么测试没发现

幸福路径：集合小，排空跟得上。  
实验室连接若都会互相宣布，看不见 spy 放大。2023-05 是主网活动把它暴露出来。

## 5. 修复

PR #27610：1）更早丢掉已不在内存池的交易；2）集合越大，排空越快。升级到 ≥ 25.0。

## 6. 「不确定」若同类

1. 「我准备告诉你的目录」必须能丢掉过期对象，排空必须跟得上增长。
2. 为了不泄漏「我先看见哪笔」而排序，是隐私/公平选择；排序代价必须有界。
3. 只听不讲的对等节点不要写成攻击者才能连上；默认拓扑就要扛。
4. 后量子交易更大、更少进一条 INV，集合更容易积压。

## 7. 回归测试

形状（不是利用包）：待宣布集合在对方从不宣布、池里进出很快时，排序时间必须有上限，新块仍能被处理。不得把「测试对等节点都会回 INV」写成 PASS。
