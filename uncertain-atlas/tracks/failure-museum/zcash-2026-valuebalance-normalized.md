# 失败案：反序列化归一化成零不是编码必须为零；检查跑在改写后的字段上不是规则已经开火

层：**协议 + 实现**（v4 反序列化器在无 Spend / Output 时把 `valueBalanceSapling` 改写成 0；共识「必须为 0」的检查看见的是改写后的零；Zebra 按规范拒编码）

官方披露：

- Zcash 规范级 ZIP：[ZIP 256](https://zips.z.cash/zip-0256)。规范澄清写入 § 7.1.2。本页只采用 ZIP / 规范已写出的句子。无独立 CVE 号写入本条。

**事实（官方原文能对上的句子）：**

- v4 交易反序列化器接受「没有 Spend、没有 Output，但 `valueBalanceSapling` **编码非零**」的交易。
- 该值在反序列化时被**归一化成零**，于是本该拒绝的共识检查跑在归一化后的零上，**从不开火**。
- Zebra 在反序列化时按规范 § 7.1.2 拒绝该编码，畸形编码会造成共识分裂。
- zcashd 后来在反序列化时拒绝，与 Zebra 对齐。官方写这是恢复与规范、与另一实现的一致，**不是新共识规则**。
- 规范澄清：`valueBalanceSapling` 指交易里**编进去的值**，不是归一化之后的值，也不是 Sapling 池余额符号。

本页不写怎样拼无 Spend/Output 的非零余额、不抄发布线版本进不确定常量。归一化成零，不是编码必须为零。

## 1. 发生了什么

门卫说：没带货，余额栏必须写零。  
进门之前，有人把余额栏改成零再给门卫看。  
门卫看见零，放行。  
栏上原来写的不是零。  
门卫放行，不是规则已经验过编码。  
另一家门卫看的是纸面上的数字，直接拒。  
两家对同一份字节，一个收、一个拒。

## 2. 根因

共识检查吃的必须是**规范编码对象**，不是反序列化器顺手改过的本地结构。  
「必须为 0」若跑在已经被写成 0 的字段上，失败分支不可达。  
规范对象是编码；本地结构是实现。把本地结构当规范，规则变装饰。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 3 / CVE-2021-39137 | 别名错根；本页是反序列化改写后再检查 |
| 不变量 12 | 同根不同列表；本页是字段被改写后检查永远绿 |
| 不变量 102 / ZIP 257 | 电路 ≠ 陈述；本页是编码 ≠ 归一化 |
| 不变量 104 | 重复头复位跟踪；本页是反序列化改写余额栏 |
| 不变量 13 | 验证明 ≠ 供给；本页是检查看见的不是编码 |
| 本页 | **归一化成零 ≠ 编码必须为零；检查跑在改写后的字段上 ≠ 规则已经开火；一家拒一家收 ≠ 多实现已经同根** |

## 3. 被破坏的 invariant

- 共识检查必须看见规范编码，不得先把字段改成会让检查永远通过的值（不变量 105）
- 「必须为 0」指编码，不是反序列化之后的本地零
- 两实现对同一编码必须同拒或同收

## 4. 为什么测试没发现

幸福路径：诚实钱包在无 Spend/Output 时把余额栏写成 0。  
绿测试只覆盖「已经是零，检查通过」。  
边角要：编码非零、无 Spend/Output；检查读的是编码还是本地结构；第二实现是否拒。

## 5. 修复

官方：zcashd 在反序列化拒绝该编码，与 Zebra、与 § 7.1.2 对齐。  
规范加注：字段名指编码，不指归一化值，不指池余额。  
官方定性：恢复一致，不是改规则。

## 6. 「不确定」若同类

1. 第一版可以不做屏蔽余额栏 / v4 兼容路径。
2. 若字段「在某条件下必须为 0」：检查必须读编码字节（或与编码一一对应的未改写结构）。
3. 反序列化可以拒，不得先改再验。改写后的零不是规则已执行。
4. 第二实现已拒，不是第一实现已经安全；对齐是修法，不是「规范变了」。
5. 这和确定性别名（3）、同根不同列表（12）、跟踪复位（104）、电路≠陈述（102）不是同一句。
6. 不要写怎样拼非零余额栏。不要抄版本号。

## 7. 回归测试

形状（不是利用包）：文案把归一化成零写成编码必须为零已经成立必须红。把检查跑在改写后的字段上写成规则已经开火必须红。把一家拒一家收写成多实现已经同根必须红。把恢复一致写成规范改了规则必须红。与 3 / 12 / 102 / 104 糊成一句必须红。

**事实来源：** [ZIP 256](https://zips.z.cash/zip-0256)；规范 § 7.1.2 澄清句。
