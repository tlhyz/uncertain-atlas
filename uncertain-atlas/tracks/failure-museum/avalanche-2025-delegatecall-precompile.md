# 失败案：正确实现了 EVM 的 DELEGATECALL 语义不是预编译的信任模型已经跟着改过

层：**协议 + 实现**（有状态预编译长期按「允许委托调用、但不兑现 EVM 委托语义」的未写明假设工作；换上正确兑现语义的执行库之后，调用者身份按 EVM 规则变成了调用合约，特权入口被冒充）

官方披露：

- Ava Labs Academy：[The DelegateCall Incident](https://academy.avax.network/blog/delegatecall-incident)（2025）。无独立 CVE 写入该页。无 AvalancheGo GHSA 列表项。

**事实（官方原文能对上的句子）：**

- Trail of Bits 在审计 `libevm` 与 `subnet-evm` 时，于 2025-07-29 问有状态预编译怎样处理 `delegatecall`。次日本地测试确认行为不正确，升级为 P1-Critical。
- 洞随 AvalancheGo 引入 `libevm` 的那条发行线进入产品。恶意合约对有状态预编译做 `delegatecall` 时，可以冒充它的调用者；任何调用了该恶意合约的账户，都可能在这次调用里被伪造成对有状态预编译的调用方。
- 根因不是「库写错了 EVM」。官方写：有状态预编译长期允许 `DELEGATECALL`，却假定 EVM 的委托语义**不会**被兑现；`libevm` **正确**兑现了委托语义。预期（委托语义被忽略）与实际（委托语义被执行）错位，才变成冒充。
- 同一条语义也覆盖 `callcode`。
- 永久修法在 Granite 升级（主网 2025-11-19）：现有有状态预编译若经 `delegatecall` / `callcode` 进来则显式 `revert`；底层库把「EVM 语义调用者」和「原始调用者」拆开，避免以后的预编译再踩同一类。
- 官方还写了先发热修、再上永久升级。热修不是谓词本来就齐。
- 本页不把版本号抄进不确定常量。Native Asset Call（2022）是另一案，本页不混写。

本页不写怎样拼冒充合约，不抄版本 / 开关 / 预编译地址。

## 1. 发生了什么

旧厨房假定：这扇特权门虽然标着「别人可以代你按」，按下去时柜台仍认门口那个人。  
新厨具按说明书做：代按就是柜台认代按的人。  
说明书对了，厨房的信任模型没改。  
于是恶意代按的人，被柜台当成了被代的那个人。  
库实现正确，不是旧假设已经更新。  
热修关上这扇门，不是所有特权入口已经分清两种调用者。

## 2. 根因

有状态预编译是链上的特权入口，调用者身份是授权对象。  
EVM 的 `DELEGATECALL` / `CALLCODE` 会改「柜台看见的调用者」。  
长期未写进规范的假设是：这扇门允许这两种调用，但不会按 EVM 改调用者。  
换上正确兑现语义的库之后，假设被执行，不是库写错了。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 117 | 预编译失败留下半笔；本页是成功路径上的调用者身份 |
| 不变量 118 | 嵌套更新外层看不见；本页是委托调用改了 `caller` |
| 不变量 81 | 授权代发漏掉内层校验；本页是 EVM 调用语义 vs 预编译信任 |
| 不变量 113 | 跨共识消息静默省略 origin 指令；本页是同机 EVM |
| 不变量 103 | OOG 删户没回滚；本页不是失败路径 |
| Native Asset Call 2022 | 另一条官方故事；本页不混 |
| 本页 | **正确兑现 EVM 委托语义 ≠ 预编译信任模型已经跟着改过；库换了正确语义 ≠ 旧假设已经更新** |

## 3. 被破坏的 invariant

- 有状态预编译若允许委托调用，必须写清授权看的是 EVM 语义调用者还是原始调用者；对不上必须拒（不变量 119）
- 正确兑现字节码语义不是特权入口的信任模型已经同步
- 热修 / 硬升级不是谓词本来就齐，只是后来补上了

## 4. 为什么测试没发现

幸福路径：普通 `CALL` 进有状态预编译，调用者就是发起账户。  
旧实现把「委托调用被忽略」当成默认，绿测试不踩委托。  
换库之后，正确语义第一次被执行，未写明的假设才爆。  
边角要：经 `delegatecall` / `callcode` 进入特权预编译时，授权对象是谁；两种调用者字段是否被拆开。

## 5. 修复

官方：先热修，再在 Granite 主网升级里做两处永久修——委托进来则 `revert`；库拆开 EVM 语义调用者与原始调用者。  
热修不是所有预编译已经分清两种调用者。永久修的「拒绝委托」是收紧入口，不是「委托语义本来就不该兑现」。

## 6. 「不确定」若同类

1. 第一版可以不做通用 EVM、有状态预编译、委托调用进特权入口。
2. 若一层引擎把字节码调用约定接到特权预编译：必须先写授权看哪一种调用者，或入口直接拒绝委托。
3. 换了「更正确」的执行库，必须重审所有未写明的旧假设；正确兑现语义不是信任模型已经更新。
4. 这和预编译半写入（117）、嵌套外层看不见（118）、授权代发（81）、XCM origin（113）不是同一句。
5. 不要写怎样冒充。不要抄版本 / 开关 / 地址。不要把 2022 Native Asset Call 糊进本页。

## 7. 回归测试

形状（不是利用包）：文案把正确兑现 `DELEGATECALL` 语义写成预编译信任模型已经跟着改过必须红。把库换了正确语义写成旧假设已经更新必须红。把热修 / 硬升级写成谓词本来就齐必须红。与 117 / 118 / 81 糊成「预编译调用者」一句必须红。
