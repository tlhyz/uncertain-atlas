# 失败案：ASA-2024-002 单笔 CheckTx 绿不是整包可提案

层：**协议 + 实现**（Prepare 产出的列表必须能被诚实 Process 收下；不是四门定义本身）

官方披露：Cosmos SDK [ASA-2024-002 / GHSA-2557-x9mg-76w8](https://github.com/cosmos/cosmos-sdk/security/advisories/GHSA-2557-x9mg-76w8)。咨询标 **Medium / Moderate**，影响写成 Denial of Service。受影响：`<= 0.50.3`、`<= 0.47.8`。补丁：`0.50.4`、`0.47.9`。本页不另编 CVE——咨询未给 CVE ID。

**事实（官方原文能对上的句子）：**

- 同时使用默认 `PrepareProposalHandler` **和** 默认 `SenderNonceMempool` 时，存在一个问题。
- 单一发送者在**某些条件**下放入多笔**序号不连续**的交易，可能让节点提出**非法块**。
- 一旦进入这种状态，可能导致网络**出块减少**。
- 官方定性：拒绝服务。

本页不写「某些条件」具体是哪几步，不写怎样排不连续序号，不抄版本号当不确定常量。

## 1. 发生了什么

池里每笔都过了 CheckTx。默认装箱手按发送者序号去抓。  
序号中间有洞。默认 Prepare 仍可能把这包交出去。  
诚实 Process 不收。提议者白忙，出块变慢。  
单笔「能进池」被当成「整包能过验收」。

## 2. 根因

CheckTx 看的是**一笔**此刻能不能进本节点池。  
Prepare 看的是**一包**能不能当本轮提案。  
按发送者序号组织的内存池，不连续序号会让「池里有」和「可提案前缀」不是同一集合。默认助手没有把这两句钉死。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 33 | 四门必须分开；诚实 Prepare 的提案，诚实 Process 必须 Accept |
| 不变量 63 / ASA-2023-002 | 默认 MaxBytes 不是第一轮活性 SLA |
| 不变量 68 / ASA-2024-006 | 注入扩展不是投票权预言机 |
| 不变量 44 | 入池前拒绝的验代价 |
| 本页 | **单笔 CheckTx 绿 ≠ 整包可提案；序号洞不得变成非法块** |

## 3. 被破坏的 invariant

- Prepare 产出的列表必须是诚实 Process 会 Accept 的（不变量 69）
- 按发送者序号装箱时，不得因序号不连续而提出非法块
- 单笔 CheckTx 成功不得写成整包已可提案

## 4. 为什么测试没发现

幸福路径：每个发送者的序号连续，或每轮只从一人取一笔。  
只测「每笔 CheckTx 绿」会过，看不见「装箱后 Process 拒」。  
默认两件套被当成「规范已经配对」。

## 5. 修复

官方：升级到补丁版本。咨询没有写无代码绕过。  
换掉其中一个默认件（自写 Prepare，或不用 SenderNonceMempool）也不等于新产品句已经写清。自己配对时仍要测「有洞的序号」。

## 6. 「不确定」若同类

1. 若账户/序号模型进池：必须写清 Prepare 取出的是**可验收前缀**，不是「池里所有过 CheckTx 的笔」。
2. 诚实 Prepare 的输出，诚实 Process 必须 Accept。这是不变量 33 的产品测法；本条是默认两件套曾经做不到。
3. 不要把 Cosmos SDK 默认 handler / 默认 mempool 写成规范保证。
4. 这和四门定义（33）、块上限 SLA（63）、注入扩展权重（68）不是同一句。
5. 后量子验签更贵时，更不能让「装箱失败 → Process 拒 → 再开一轮」当正常路径。

## 7. 回归测试

形状（不是利用包）：文案把「每笔 CheckTx 绿」写成整包可提案必须红。同一发送者序号不连续、默认 Prepare 仍提出 Process 会拒的块仍标 PASS 必须红。只测连续序号不得标「默认两件套已安全」。
