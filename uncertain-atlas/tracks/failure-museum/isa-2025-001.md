# 失败案：ISA-2025-001 / ASA-2025-004 跨链确认的 JSON 反序列化不是已经确定

层：**协议 + 实现**（acknowledgement 反序列化必须确定性；不是一般「Apply 要确定」，也不是外层交易解码）

官方披露（同一问题的两页）：

- 先发：[ASA-2025-004 / GHSA-jg6f-48ff-5xrw](https://github.com/cosmos/ibc-go/security/advisories/GHSA-jg6f-48ff-5xrw)。咨询标 **Critical**。补丁：`v7.9.2`、`v8.6.1`。
- 后发：[ISA-2025-001 / GHSA-4wf3-5qj9-368v](https://github.com/cosmos/ibc-go/security/advisories/GHSA-4wf3-5qj9-368v)。咨询正文标 **High**（GitHub 列表徽章标 Critical）。补丁：`v7.10.0`、`v8.7.0`。官方写：这是前一补丁的**扩展**，把同一保护扩到 **transfer 之外的所有应用**。

受影响：IBC-Go `>= v7`；更早版本 **MAY / may** 也受影响。本页不另编 CVE——两页都未给 CVE ID。

**事实（官方原文能对上的句子）：**

- IBC-Go **反序列化 acknowledgement** 时出现**非确定性**行为，可以**停链**。
- **任何能打开 IBC 通道的用户**都可以把这种状态引进链。
- 绕过：把 **Channel Opening 做成需许可**。
- ASA-2025-004：补丁一般**不破坏状态**，除非依赖会先反序列化再序列化 ack 再交给 transfer 的中间件；那种中间件「很少见」。若中间件自己编 ack 且与 transfer 应用不一致，滚动升级会停、全员升级后经该中间件的转账会失败。那时必须改用 ibc-go 的 codec，且这次改编码是**状态破坏**，要**协调升级**。官方曾撤回当天更早的发布，因为误约束了 **receive** 包的编解码，常见中间件会坏；新补丁只保留对 **acknowledgement** 的约束。
- ISA-2025-001：除非补丁铺开前已有利用（那时会像没补一样停），否则**不破坏状态**，可以滚动升级。

本页不写怎样构造 acknowledgement、不抄 JSON 字段顺序、不把 Cosmos Hub / Osmosis / PFM / ibc-hooks 写成那些产品的规范保证、不抄版本号当不确定常量。第一版可以不装 IBC。

## 1. 发生了什么

对岸回了一张「收到了」的条子。  
两边用 JSON 拆这张条子。拆法不是同一把尺。  
有的节点拆成甲，有的拆成乙。状态对不上，高度停。  
谁能开一条 IBC 通道，谁就能把这张条子送进来。  
只修了转账应用不够：别的应用也拆同一类条子。

## 2. 根因

跨链确认被当成「意思对了就行」。  
意思对了、字节不同，诚实节点会走出两个世界。  
能开通道 = 能往提交路径塞这种不确定对象。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 3 / L1.4 | 同一已排序输入，两实现状态哈希相同（一般确定性） |
| 不变量 70 / ASA-2024-0012 | 外层交易上限不是内层解码已有界 |
| 不变量 71 / ISA-2025-002 | 可选模块 EndBlocker 出错会停链 |
| 不变量 76 / ASA-2024-010 | Int/Dec 位宽必须对齐 |
| 不变量 79 / Dragonberry | ICS-23 验通过 ≠ 叶子已在原树 |
| 本页 | **跨链 acknowledgement 反序列化必须确定性；能开通道的用户 = 能引入停链状态的集合** |

## 3. 被破坏的 invariant

- 跨链确认的反序列化必须确定性（不变量 77）
- 能打开通道的用户集合就是能引入停链状态的集合
- 只补 transfer 不是所有应用已经安全

## 4. 为什么测试没发现

幸福路径：两边用同一库、同一字段顺序，JSON 碰巧一致。  
只测「ack 意思是成功」会绿，看不见「字节不同 → 停链」。  
中间件自己再编一次 ack，幸福路径更绿、分叉更晚。

## 5. 修复

官方：用规定 codec 反序列化 ack；升到对应补丁。ISA-2025-001 把保护扩到所有应用。  
许可制开通道是绕过，不是反序列化已经确定。  
自己写中间件：ack 必须与应用同一 codec；改编码可能变成协调升级。

## 6. 「不确定」若同类

1. 第一版可以不装 IBC / 跨链确认。
2. 若装：acknowledgement 必须有唯一字节；反序列化失败必须拒，不得非确定。
3. 能开通道的主体必须写成活性对手。许可开通道是部署减面，不是谓词已齐。
4. 只测 transfer 不够。每个会拆 ack 的应用都要测。
5. 这和一般确定性（3）、外层解码（70）、可选模块 EndBlocker（71）、ICS-23 soundness（79）不是同一句。
6. 不要抄中间件名单。不要把官方在某条主网测过写成那些链的规范。

## 7. 回归测试

形状（不是利用包）：文案把「ack 意思对」写成反序列化已确定必须红。能开通道的用户引入非确定 ack、高度停仍标 PASS 必须红。只测 transfer、其它应用未扫仍标「已全覆盖」必须红。把 ASA-2025-004 写成 ISA-2025-001 已包含所有应用必须红。
