# 失败案：ASA-2024-010 Int 与 Dec 位宽对不齐不是已对齐的数

层：**实现 + 协议**（会互转的数值类型必须对齐最大位宽；不是输出求和拒块，也不是奖励池溢出）

官方披露：Cosmos SDK [ASA-2024-010 / GHSA-7225-m954-23v7](https://github.com/cosmos/cosmos-sdk/security/advisories/GHSA-7225-m954-23v7)。咨询标 **High**。受影响：`cosmossdk.io/math` `<= math/v1.3.0`。补丁：`v1.4.0`。本页不另编 CVE——咨询未给 CVE ID。

**事实（官方原文能对上的句子）：**

- `sdk.Int` 与 `sdk.Dec` 的**位宽不对齐**，在 **Int 上下文里使用 Dec** 时，可能 **panic**。
- 修法：在 `cosmossdk.io/math` 里**对齐**两类数据的最大尺寸。
- 影响该库的消费者，咨询点名包括 **IBC-Go** 与 **tokenfactory（permissionless）**。本页不把这两条写成那些产品自己的规范保证。
- 从 `v1.3.0` 升到 `v1.4.0`：**可以不硬分叉**，只改 `go.mod`。
- 咨询注：若当前**低于** `v1.3.0`，升到 `>= 1.3.0` 之前必须先做**协调升级**。

本页不写位宽数字、不写怎样构造 Dec、不把 IBC-Go / tokenfactory 写成不确定已选用、不抄版本号当常量。

## 1. 发生了什么

账本里有两种「数」：整数、小数。  
它们本该能互相交给对方。  
一边能装的位数比另一边多。小数走进整数的房间，实现慌了，进程倒下。  
这不是「金额加爆了所以拒交易」。是类型边界没对齐。

## 2. 根因

「能转换」被当成「上界已经同一把尺」。  
库的补丁可以只是依赖号（官方：1.3.0→1.4.0 不必硬分叉）。  
更旧的线升上来，官方要求先协调升级——说明数学库的位宽一旦被状态吃进去，就可能变成共识。

这不是：

| 案 | 对象 |
|----|------|
| 不变量 7 / CVE-2010-5139 | 输出求和溢出必须拒绝 |
| 不变量 51 / CVE-2025-46597 | 尺寸检查必须用固定宽度整数 |
| 不变量 74 / ISA-2025-005 | 奖励池入金溢出可以停链 |
| 本页 | **会互转的 Int/Dec 必须对齐最大位宽；Dec 进 Int 不得 panic** |

## 3. 被破坏的 invariant

- 会互相转换的数值类型必须对齐最大位宽（不变量 76）
- Dec 进 Int 上下文不得 panic
- 数学库补丁是否要硬分叉，以该官方页为准，不得发明

## 4. 为什么测试没发现

幸福路径：两边都用小正数，碰不到较短的那条上界。  
只测「1 + 1 能转成小数」会绿，看不见「Dec 的上界大于 Int」。  
依赖库被当成「不是共识」。

## 5. 修复

官方：对齐最大尺寸；升到补丁版本。1.3.0→1.4.0 可只改依赖。更低版本先协调升级。  
自己换一套 Int/Dec 仍要测「较短上界的那边吃到较长那边的值」。

## 6. 「不确定」若同类

1. 第一版：金额只用一种规范整数。不要同时暴露两套可互转、上界不同的数。
2. 若必须有小数：先写同一条最大位宽，再写转换。转换失败必须拒，不得 panic。
3. 数学库一旦写进状态，升级路径必须点名：只改依赖，还是要协调升级 / 硬分叉。以官方该页为准，不要抄 1.3.0。
4. 这和输出求和拒块（7）、固定宽度尺寸（51）、奖励池溢出停链（74）不是同一句。
5. 不要把「permissionless tokenfactory」写成不确定 v1。

## 7. 回归测试

形状（不是利用包）：文案把 Int/Dec 写成位宽已对齐、但 Dec 进 Int 仍 panic 仍标 PASS 必须红。只测小整数转换不得标「数学库已安全」。把 1.3.0→1.4.0 写成必须硬分叉必须红（与该页原文相反）。低于补丁线升上来却不写协调升级必须红。
