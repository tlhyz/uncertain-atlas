# 模式：把基本过滤器三件事说成三个名字

**层次**：轻客户端 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[BIP-158](https://github.com/bitcoin/bips/blob/master/bip-0158.mediawiki)。  
**例**：[基本过滤 ≠ 已经相关](../../tracks/light-clients/worked-example-basic-filter-vs-relevant.md)。

## 三个名字

1. **脚本集合：** 上一份花费脚本 + 本笔收款脚本；不是已经有交易，也不是已经有附言。
2. **概率匹配：** 集合里必中，集合外也可能中；看见对上不是已经相关。
3. **排除附言留承诺路：** 给以后的软分叉承诺留位置；不是已经写进共识。

## 为什么要分开叫

官方把装什么、假阳性、以后能不能承诺写进一次过滤器构造，但每一件钉的是不同旋钮。把它们叫成一个「对上了就是我的付款」，会把 157 的索取、布隆和只看头就放货一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果做基本过滤器，先数清问的是装了什么、假阳性，还是共识承诺，再决定要不要同一次发布。
