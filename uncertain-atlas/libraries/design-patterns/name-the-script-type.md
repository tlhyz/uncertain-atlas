# 模式：把多签层次三件事说成三个名字

**层次**：应用 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[BIP-48](https://github.com/bitcoin/bips/blob/master/bip-0048.mediawiki)。  
**例**：[脚本类型 ≠ 已经是账户层](../../tracks/implementation/worked-example-script-type-vs-account.md)。

## 三个名字

1. **不搬家：** 看见现有多签派生习惯不是已经要搬家，也不是已经可以改路径。
2. **脚本类型：** 看见脚本类型层不是已经是账户层；看见本页不是已经每来一种脚本都要再写一份 BIP。
3. **排序：** 看见本页多签不是已经不排序，也不是已经是单签账户路径。

## 为什么要分开叫

官方把业界已经在用的习惯写成标准，又另开脚本类型层给以后的脚本往下加，还把确定性排序写成支持本页就自带。把它们叫成一个「看见多签路径就已经是账户发现」，会把嵌套单签找回和用途层一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果导出多签，先数清问的是现有习惯还能不能用、脚本类型在哪一层，还是公钥已经排过，再决定要不要同一次发布。
