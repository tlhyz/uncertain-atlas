# 模式：把付款协议三件事说成三个名字

**层次**：应用 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[BIP-70](https://github.com/bitcoin/bips/blob/master/bip-0070.mediawiki)。  
**例**：[付款请求 ≠ 已经是回执](../../tracks/lifecycle/worked-example-request-vs-ack.md)。

## 三个名字

1. **付款请求：** 看见付款请求 / 商家名字 / 证书身份不是已经授权，也不是已经是那条地址。
2. **付款报文：** 看见付款报文 / 里面有签过的交易不是已经是回执，也不是商家已经收下。
3. **回执：** 看见回执 / 「已收到」那句备忘不是已经最终，也不是已经确认。

## 为什么要分开叫

官方把核身份、核过期、再问顾客写成三步，又把顾客广播、送到付款网址、商家自己判断是否满足写成不同对象，还把回执备忘写成处理中的状态。把它们叫成一个「看见商家请求就已经最终」，会把付款 URI 已经授权一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果让商家和顾客对消息，先数清问的是请求、报文还是回执，再决定要不要同一次发布。
