# 模式：把头版本栏三件事说成三个名字

**层次**：实现 / 命名。  
**分类**：事实（官方标注）+ 建议（产品）。  
**来源**：[Core Data Structures](https://github.com/cometbft/cometbft/blob/main/spec/core/data_structures.md) Header / Version。  
**例**：[Header.Version 是应用与块版本 ≠ 已经知道是哪一版的什么](../../tracks/implementation/worked-example-headerversion-vs-whole.md)。

## 三个名字

1. **`Header.Version` 是「应用与块版本」不是已经知道是哪一版的什么：** 官方在这一节顶上写明它**更确切地说是共识版本**，且**不含 P2P 版本**。
2. **`Version.Block` 必须全网一致不是 `App` 也走同一条：** `Block` 要整个运行网络一致；`App` 由应用决定。同一张表，两种权威来源。
3. **一个版本号不是已经点名了整个协议：** 官方在这里留了**两条 TODO**，版本通论尚未成文。

## 为什么要分开叫

官方把「这一栏是什么」「两个子字段各自谁定」「这一节还欠什么」写成三件事。把它们叫成一个「看见版本号就知道是哪一版」，会把共识版本与 P2P 版本、网络一致与应用自定、以及版本通论尚未成文这三层一起吞掉 —— 而第三条尤其要紧：**这一节自己声明了它不完整**。

## 产品

**建议（产品，不是事实）**：产品句**不得只写一个版本号就声称「协议版本已点名」**，必须说明是块版本、应用版本、P2P 版本还是 ABCI 版本，并写出处。若产品文案说「版本已对齐」，先数清问的是 Header.Version 是应用与块版本不是已经知道是哪一版的什么、Block 必须全网一致不是 App 也走同一条，还是一个版本号不是已经点名了整个协议。
