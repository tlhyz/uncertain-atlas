# 设计模式：先点名扩展密钥

## 一句话

看见分层钱包导出，先问：这一串是扩展公钥、扩展私钥，还是已经能花的那一把。不要把能推子钥写成已经是地址，也不要把看见扩展公钥写成已经有 UTXO。

## 问题

`xpub`、`地址`、`能花`、`UTXO`、`HD` 会被叠成一个词。BIP-32 把扩展公钥写成可以分享、但不带花费能力的对象，正是为了不让「能看进账」听成「已经能签字」。

## 做法

1. 先写扩展密钥种类：公钥还是私钥。
2. 再写硬化：这一支能不能从公钥父节点推出。
3. 再写编码：这是树节点，还是已经编成收款地址。
4. 最后才问：链上有没有对应输出，以及手里有没有花费能力。

## 不要和谁弄混

- 不要和 [`name-the-address-object.md`](name-the-address-object.md) 弄混：那一页管的是看见地址 ≠ 已经有 UTXO；本页管的是看见扩展公钥 ≠ 已经能花。
- 不要和 [`name-the-checksum-version.md`](name-the-checksum-version.md) 弄混：那一页管的是校验和版本。
- 不要和 [`name-the-psbt-role.md`](name-the-psbt-role.md) 弄混：那一页管的是未完成交易对象。

## 对 Uncertain 的建议

第一版如果导出分层钱包，先点名「扩展公钥」和「花费能力」。不要默认能看进账就是能花，也不要默认链节点标识已经是收款地址。
