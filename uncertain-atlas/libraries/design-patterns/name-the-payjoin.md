# 模式：把 payjoin 三件事说成三个名字

**层次**：应用 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[BIP-78](https://github.com/bitcoin/bips/blob/master/bip-0078.mediawiki)。  
**例**：[带 pj= 的付款 URI ≠ 已经是 payjoin 付款](../../tracks/lifecycle/worked-example-payjoin-vs-original.md)。

## 三个名字

1. **端点：** 看见带 `pj=` 的付款 URI 不是已经是原始包，也不是已经是提案，也不是已经是 payjoin 付款。`pjos=0` 是另一条信号。
2. **原始包 / 提案 / 交易：** 看见原始包不是已经是 Payjoin 提案，也不是已经是 Payjoin 交易。
3. **加输入不是另开一笔：** 看见收款方加了输入不是已经另开一笔，也不是已经对全网私人，也不是已经能再当原始包。

## 为什么要分开叫

官方把 `pj=` 写成端点描述，把原始包、提案、交易写成三道门，又把收款方整理未花输出写成不另开交易，还把探测和再入写成必须挡。把它们叫成一个「看见 pj= 就已经是 payjoin 付款」，会把付款 URI 已经授权和部分签名包已经能广播一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果让收款方往付款里加输入，先数清问的是端点、原始包 / 提案 / 交易，还是加输入是不是已经另开一笔，再决定要不要同一次发布。
