# 模式：把造提案时收交易三件事说成三个名字

**层次**：共识 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[Creating a proposal](https://github.com/cometbft/cometbft/blob/main/spec/consensus/creating-proposal.md)。  
**例**：[先装证据 ≠ 已经装满交易](../../tracks/consensus/worked-example-evidence-vs-reap.md)。

## 三个名字

1. **证据优先：** 看见未处理的证据优先于内存池交易不是已经装满交易，也不是已经执行。
2. **两条上限：** 看见提案扣掉证据后的交易上限不是已经和内存池假定没有证据的上限同一条。
3. **写成 -1：** 看见 MaxBytes 写成 -1 不是已经没有上限，也不是应用已经可以随便回。

## 为什么要分开叫

官方把证据优先写成装块顺序，把提案扣掉证据和内存池假定没有证据写成两套上限，又把「整池都给 Prepare」和「应用仍不得超过 MaxTxBytes」写成两件事。把它们叫成一个「看见先装证据就已经装满交易」，会把四门和默认 MaxBytes 一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果让应用改提案，先数清问的是证据占位、哪一条上限，还是写成 -1，再决定要不要同一次发布。
