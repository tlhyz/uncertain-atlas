# 模式：把对等功能协商三件事说成三个名字

**层次**：网络 / 命名。  
**分类**：事实（官方拆法）+ 建议（产品）。  
**来源**：[BIP-434](https://github.com/bitcoin/bips/blob/master/bip-0434.md)。  
**例**：[协议版本 ≠ 已经启用功能](../../tracks/network/worked-example-feature-vs-enabled.md)。

## 三个名字

1. **版本门槛：** 协议版本够了不是已经支持某项功能，也不是已经实现本页。
2. **通告：** 看见 `feature` 不是已经启用，也不是已经理解。
3. **协商窗：** `version` 与 `verack` 之间才是本页；`verack` 之后才来的不是已经是本页协商。

## 为什么要分开叫

官方把「不必再协调改协议版本」写成动机，同时又要求忽略不支持的标识，并把发送窗钉在 `verack` 之前。把它们叫成一个「版本号够了就已经会」，会把头通告、wtxid 通告和停交易转发一起吞掉。

## 产品

**建议（产品，不是事实）**：不确定第一条结算机如果写对等升级，先数清问的是版本门槛、通告还是已经启用，再决定要不要同一次发布。
