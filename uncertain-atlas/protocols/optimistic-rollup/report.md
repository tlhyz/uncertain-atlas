# 乐观 Rollup · 19 节档案（第一版，Arbitrum / Optimism 对照）

独特思想过滤器：Bitcoin / CometBFT / Ethereum L1 都没有「先公布执行结果、限期内揭穿」这套结算缝。  
本档案写**品类结构**。两家产品的证明游戏、升级、逃生舱在演化，版本敏感句一律标「以该链现行规范/合约为准」。  
禁止 TVL、官网 TPS、营销「Equivalence」。

---

## 1. 一句话定义

租户执行环境产出状态根 R 与批次数据（或数据承诺）。结算层合约在争议窗口内接受「R 为真，除非有效欺诈/过错证明」。窗口结束且规则允许则兑付。

---

## 2. 它解决的问题

L1 通用计算贵、状态胀。把执行挪走，L1 只做：排序承诺、DA 锚点、争议裁判、桥。  
代价：用户的「到了」从一层变成多层；排序者与揭穿人成为新角色。

---

## 3. 架构图

```text
用户 tx → 排序者（常见中心化）
              ↓
        L2 执行 → 新状态
              ↓
        批次数据 → L1 calldata / blob / 其他 DA
        状态根  → L1 合约
              ↓
        争议期：挑战者下载数据、重放、交互证明
              ↓
        窗口结束 → 桥允许提款（若合约如此写）
```

Optimism 与 Arbitrum 都落在这张图里。差别主要在**争议协议的轮次与证明机**，不是「一个是 rollup 一个不是」。

---

## 4. 一笔交易完整生命周期

1. 用户签 L2 交易（域必须与 L1 分开，见 domain-separation）。  
2. 排序者收入、排序、在 L2 执行。UI 常在此显示成功。  
3. 批次提交 L1：数据 + 根。此时 L1 头可能尚未最终。  
4. L1 最终 ≠ 争议结束。OP Stack 另有三颗推导头：`unsafe` / `latest` 不是已经从 L1 推导；OP `safe` 不是 Gasper justified；L2 `finalized` 不是桥已经兑付。精读：[`../../tracks/finality/worked-example-unsafe-vs-derived.md`](../../tracks/finality/worked-example-unsafe-vs-derived.md)（不变量 141）。  
5. 提款：按该桥，可能等待窗口、证明、Merkle 包含。官方文档写 Standard Bridge 等待不是 L2 交易还没 finalized。  
6. 若排序者审查：用户能否强制从 L1 inbox 插入——**产品相关，必须读合约**。

**事实：** 步骤 2 的成功是租户执行，不是结算完成。

---

## 5. 状态模型

L2 自己的账户/合约树（常为 EVM 兼容，这是生态选择不是品类必然）。  
L1 只存：根、消息、桥余额。  
双花：在 L2 规则下花两次，若无人揭穿且数据不可用，桥可能按假根兑付。

---

## 6. 共识

**L2 排序**不是 CometBFT。常见是中心化排序 + L1 上的先后顺序作为最终仲裁原料。  
**L1 共识**提供最终性与裁判。  
不要写「rollup 有自己的 BFT 所以和 Cosmos 一样」。有的产品叠加委员会，那是额外假设。

---

## 7. 执行

乐观：L2 先跑。争议时在 L1 或交互协议里重放**被挑战的步**（单轮或多轮，产品演化）。  
**invariant：** 诚实挑战者在数据可用且窗口足够时，能否定假根。  
实现把窗口、gas、超时写错，invariant 只在纸上。

---

## 8. 网络

用户 ↔ 排序者 RPC 是中心点。  
批次向 L1 传播走 L1 网络。  
挑战者必须能发现根、下载体、提交证明——发现与审查在部署层。

---

## 9. 存储

L2 全节点存 L2 状态。  
L1 存根与（短时）blob。blob 过期后，历史 DA 靠谁档案，是另假设（L5.4）。  
AnyTrust 父链常见只收 DACert，全文在委员会抽屉：[`../../tracks/light-clients/worked-example-dacert-vs-posted.md`](../../tracks/light-clients/worked-example-dacert-vs-posted.md)（不变量 142）。证书不是已经贴上全文。  
挑战者磁盘不够或历史被删，揭穿失败。

---

## 10. 密码学

用户签、Merkle/状态根、可能的 KZG（blob）、争议过程中的哈希。  
一般**不**在乐观路径上每块验 SNARK。ZK rollup 才是那条路（L8，本档案不混）。

---

## 11. 安全假设

| 假设 | 失效 |
|---|---|
| 争议期内至少一名诚实且在线的揭穿者 | 假根变真兑付 |
| 批次数据在窗口内可下载 | 无法证明欺诈 |
| L1 结算合约正确 | 桥被直接偷 |
| 升级钥匙不作恶 / 有时限 | 规则被改成「不能挑战」 |
| 排序者活性或存在逃生舱 | 审查、卡资金 |
| L1 经济安全 | L1 重组导致批次改写 |

链（L1）**知道**：提交的根、批次承诺、争议交易。  
链**不知道**：每个 L2 用户的即时体验是否等于结算。

---

## 12. 最大结构性优势

**把执行从结算里拆出来，同时把最终裁判留在更硬的层。**  
这是模块化执行的一半（另一半是有效性证明）。结构优点是「L1 不每笔重跑」，不是「更去中心」。

---

## 13. 最大具体缺陷

1. 挑战期与资本效率互撕。  
2. 排序中心化是默认现实。  
3. 数据扣留直接打掉乐观假设。  
4. 证明游戏实现复杂度高，测试难。  
5. 用户层把 L2 确认画成 L1 最终。

---

## 14. Trade-off

| 得到 | 换 |
|---|---|
| L1 执行税下降 | 多层「到了」 |
| 兼容 EVM 生态（若选择） | 继承 EVM 状态胀与 MEV 形状 |
| 乐观：日常无证明成本 | 必须有揭穿人 + DA + 时间窗 |
| 可升级桥 | 治理即后门风险 |

## 16. 源码入口（预告）

1. L1 上提交根与数据的合约。  
2. 欺诈/过错证明入口与超时。  
3. 强制包含 / inbox。

先合约，再 L2 客户端。不要先读浏览器。

---

## 17. 关键函数（逻辑级）

**`SubmitBatch(root, data_or_commitment)`**  
invariant：提交本身不意味着可兑付。

**`ProveFraud(...)` / `ResolveChallenge(...)`**  
输入：争议位置、数据。输出：否定或维持根。  
invariant：假根 + 可用数据 + 诚实挑战 ⇒ 根被否定（在实现正确时）。

**`FinalizeWithdrawal`**  
invariant：窗口与证明条件未满足则拒。

---

## 18. 如何测试

- 假根 + 完整数据 ⇒ 挑战成功。  
- 假根 + 扣留数据 ⇒ 必须**不能**安全兑付（或明确失败）。  
- 超时、gas 耗尽、重入。  
- 两实现对同一争议步同一结果。  
「不确定」若做类似桥：这四条比 EVM 兼容测试更先写。
