## 过滤器

> 它提供了什么 Bitcoin / CometBFT / Ethereum / Solana / Sui / Aptos **很少同时具备**的思想？

**答得出（思想，不是「更快的 EVM」）：** 共识先对**交易顺序**达成一致，**不必先跑完 `Apply`**。提议者不需要本块状态根；投票者也不需要知道交易会不会 revert。文档原句形状：顺序一旦定，状态已经被决定；执行只是把已决定的结果揭开。

对照：

| 系统 | 共识当时在同意什么 |
|---|---|
| Ethereum（文档用作对照） | 顺序 **和** 执行后的状态根（执行插在共识热路径里） |
| Aptos | 仍要一个确定的串行序 `L`；STM 是实现，不是「可以不执行就投票」 |
| Solana | 领导者通常先本地执行再传播（声明锁是另一条轴） |
| 本页对象 | 本块提案可以没有本块状态根；另带 **D 块之前** 的 Merkle 根作有效性检查 |

**过不了过滤器的句子：** 「并行 EVM。」那只是执行调度，必须仍等于同一串行结果（L6.3 已钉）。本页不靠它建档。

## 文档里必须先付的代价

1. **延迟状态根。** 提案带的是 `D` 块之前的根；该根错则本块无效。文档写 `D` 是全网参数，当前测试网/主网为 3——这是部署数字，不是永恒常数。  
2. **轻节点能证的高度滞后。** 文档：对块 `N` 达成共识之后，能当官方后果去证的是 `N-D` 的状态。  
3. **本地算错会迟到才被踢。** 文档：`N-D` 执行错的节点从块 `N` 开始掉出共识，再回滚重放。  
4. **Reserve Balance。** 共识只有延迟视角，不能按「此刻余额」安全选交易；必须另写纳入规则与执行期 revert 条件。具体阈值不抄。  
5. **新账户。** 文档：零余额账户被打入资金后，要等这笔入账满 `D` 块才能自己发交易。

## 用户文案风险（目的 A）

协议对象分裂成两句：

- 共识最终：官方**顺序**已定。  
- 执行揭晓：你的余额/回执在本地 `Apply` 之后才看见。

把第一句绿勾写成「状态已经和全网一样」= 反模式 [`../../libraries/anti-patterns/order-sold-as-state.md`](../../libraries/anti-patterns/order-sold-as-state.md)。精读：[`../../tracks/consensus/worked-example-order-vs-state.md`](../../tracks/consensus/worked-example-order-vs-state.md)（不变量 136）。  
「谁写顺序」是另一根钉子（Ethereum 域外 Builder API：签盲头 ≠ 本地选交易），见 [`../../tracks/mempool/worked-example-who-orders.md`](../../tracks/mempool/worked-example-who-orders.md)。不要和「顺序已最终 ≠ 状态已最终」糊成一词。  
文档也写：节点可在块 `N` 尚未最终时**投机执行**提案，供 `eth_call` 使用。RPC 绿勾更不能当协议最终。
