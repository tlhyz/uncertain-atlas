# Nervos CKB · 19 节档案（第一版，思想级）

独特思想过滤器：Bitcoin 的 UTXO 不管「输出字节 ≤ 聪」；Ethereum 的 gas 买执行不买永占磁盘；Solana 有 rent-exempt，但是账户模型。CKB 把**原生额度、单元格字节上限、活状态集合**焊成一件事，并明确拆开**链下生成 / 链上验证**。  
资料：RFC0002（Informational / Draft 概述）、RFC0022（交易结构）。实现名与共识细节以现行 RFC / 规范为准。不写官网 TPS。  
课：L2.6。

---

## 1. 一句话定义

活状态是一组不可变 Cell。每个 Cell 的 `capacity` 限制自己的字段总字节；除 coinbase 外，输入容量之和不得小于输出容量之和。花费一次即死。

---

## 2. 它解决的问题

旧问题（RFC0002 §1、§5.1）：

- 一次手续费让状态永占全节点盘。  
- 计算导向的经济模型不适合「大部分计算在链下、一层只保管最终状态」。  
- 硬编码密码原语，换算法要软/硬分叉。

不解决：把一层变成高吞吐世界计算机。概述把自己定位成 layered 网络的保管层。

---

## 3. 架构图

```text
客户端 Generator（任意语言）
        ↓  新状态写进 outputs
交易：deps（只读活 Cell）+ inputs（引用+解锁）+ outputs（新 Cell）
        ↓
PoW / Nakamoto 变体排序（细节见 Consensus RFC，本档不杜撰）
        ↓
CKB VM 跑 lock（解锁）与 type（状态规则）
        ↓
活 Cell 集更新；占用字节受 capacity 约束
```

---

## 4. 一笔交易完整生命周期

1. 钱包在链下算好新 Cell（用户先看见结果再广播——RFC0002 称为确定交易）。  
2. 列出 deps / inputs / outputs，附解锁证明。  
3. 矿工选入块。最终性仍是概率的（最重链家族）。  
4. 节点：容量守恒、`occupied ≤ capacity`、脚本为真。  
5. 旧 Cell 死，新 Cell 活。  
6. 「到了」：与 Bitcoin 同类，要自己的确认政策，不能用品类名代替。

---

## 5. 状态模型

Cell ≈ 带定额的广义 UTXO：

- `capacity`：额度 + 字节上限  
- `data`：任意状态（可空）  
- `lock`：所有权 / 解锁  
- `type`：创建/更新时的状态规则  

冲突：同一活 Cell 作 input 两次 = 双花。  
`deps` 只读，让验证能看见依赖，便于并行（RFC0002 §4.4）。共享被很多交易读的热 Cell 仍是单行道。

---

## 6. 共识

RFC0002 §3：Nakamoto / PoW 变体，允许节点自由进出。具体改进（出块时间、叔块、NC-Max 等）**以 CKB Consensus RFC 为准**，本思想档不写未核对参数。  
**事实：** 最终性是概率的，不是 CometBFT commit。  
**建议：** 「不确定」若要确定最终，偷的是 Cell/占用/验证分离，不是再抄一套 PoW。

---

## 7. 执行

CKB VM：RISC-V 指令集（RFC0003）。脚本是无内部状态的纯函数。  
生成与验证可以不对称：客户端可以做贵的搜索，链上只做便宜的核对（RFC0002 §4.1 的排序/查找例子）。  
失败：交易无效则状态不变（概述对比「输入进 VM 再算结果」的不确定性）。

---

## 8. 网络

概述把节点分成 mining / full / light。light「信任全节点、只订自己的 Cell」（RFC0002 §6）。  
**不要**把这句话翻译成 Bitcoin SPV。产品若抄这句，必须写进用户能看见的假设。

---

## 9. 存储

活 Cell 集是当前共同知识；死 Cell 是历史。矿工节点概述称不必存全部历史，全节点验证新块。  
崩溃原子性仍是实现层（L9.3），RFC 不代替 WAL。

---

## 10. 密码学 primitive

RFC0002 §4.3：**VM 不硬编码密码指令**；默认哈希与签名也以库形式跑在 VM 上。换 Schnorr / BLS / 后量子库，理论上不必改 ISA。  
**事实：** 这是算法敏捷的结构位置。  
**推断：** 「可以部署 PQ 库」≠ 主网已经后量子，≠ 投票/出块签名已换，≠ 旧 lock 脚本自动安全。  
**建议：** 「不确定」研究「验签是插件」；不要第一版就上 RISC-V 通用 VM。

---

## 11. 安全假设（失效则什么失效）

| 假设 | 失效 |
|---|---|
| PoW / 最重链 | 重组吐出已花 Cell |
| 脚本 / VM 确定性 | 两矿工两根 |
| `occupied` 算法唯一 | 实现分裂（BIP 50 亲戚） |
| 可靠性若以后接 ZK 于 type | 屏蔽式通胀（CVE-2019-7167 同类） |
| light 信任的全节点诚实 | 用户看见假活 Cell |

---

## 12. 最大结构性优势

1. **占用一等公民：** 磁盘不是口号，是不等式。  
2. **生成/验证分离：** 用户先确认新状态；依赖可见故可谈并行。  
3. **密码原语不焊死在指令集：** 换算法的位置清楚。

---

## 13. 最大具体缺陷

1. 共识仍是概率最终，结算文案不能抄 BFT。  
2. 概述中的 light node 信任模型偏硬，与「全节点复算」不是同一产品。  
3. 最小 Cell 也有容量地板（文档常见 61 CKByte 量级——以现行规范为准，本档不当永恒常数）。  
4. 通用 `data` + 图灵完备 VM 仍可能把一层做成世界计算机，占用只改税不改欲望。  
5. RFC0002 本身标 Draft / Informational，实现已演化：数字与共识细节必须回现行 RFC。

---

## 14. Trade-off

| 得到 | 换 |
|---|---|
| 状态永占要锁额度 | 资本效率、最小占地 |
| 链下生成确定结果 | 钱包必须会当 Generator |
| 不硬编码密码 | 脚本质量、供给面、审计面变大 |
| 一层只保管 | 吞吐推给二层；跨层「到了」要另写 |

吞吐必须拆五笔账：占用压的是**存储**，不是网络切片，也不是 STM。

## 16. 源码入口（预告）

1. 输出创建：`occupied` vs `capacity`。  
2. 容量守恒（除 cellbase）。  
3. lock / type 的 VM 入口。  

先不等式，再 RISC-V。仓库路径以当时树为准。

---

## 17. 关键函数（逻辑级）

**`CheckCapacity`**  
输入：一枚 output Cell。  
输出：拒绝若 `occupied > capacity`。  
invariant：活 Cell 的字段总字节不得大于其额度。

**`CheckCapacityConservation`**  
输入：inputs/outputs（非 cellbase）。  
输出：拒绝若输出容量和 > 输入容量和。  
invariant：除协议允许的发行外，容量不凭空出现。

**`VerifyLock` / `VerifyType`**  
输入：脚本 + 交易上下文。  
输出：真/假。  
invariant：假则整笔原子失败。

---

## 18. 如何测试

- 输出字段刚好超过 capacity → 拒。  
- 输入输出容量和越界 → 拒。  
- 同一 live cell 两花费 → 拒。  
- 两实现对同一 occupied 算法必须同整数。  
- 后量子：把签名换大，看占用是否跟着涨（账本行，未测则空）。

---

## 19. 「不确定」适用性

| 档 | 内容 |
|---|---|
| 强烈建议研究 | 占用不等式；生成/验证分离；验签不焊死在 ISA |
| 可以参考 | deps 显式只读；Cell 一次花费 |
| 暂时不需要 | RISC-V 通用 VM、layered 生态、发行/二级发行表 |
| 不建议采用 | 第一版用 PoW 概率最终当结算文案；light「信任全节点」当默认验证角色；把「crypto-agnostic」写成「已后量子」 |

**建议：** 结算机 v1 先白名单字段。若以后允许任意 data，先写占用句，再谈 VM。决策列空。
