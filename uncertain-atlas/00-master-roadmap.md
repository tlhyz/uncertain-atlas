## 0. 这个项目到底在建什么

我们要建的不是「区块链名词词典」。

我们要建一台你可以反复使用的思考机器：

```
看到一个协议设计
    → 它在解决什么问题？
    → 安全假设是什么？
    → 为什么这样而不是更简单？
    → 拿什么换来了这个优势？
    → 恶意节点 / 网络分区 / 机器崩溃 / 写错一行代码会怎样？
    → 另一个客户端会不会算出不同状态？
    → 怎么证明、怎么测试？
    → 这件事适不适合「不确定」？
```

最终同时服务两个目的：

| 目的 | 成功标准 |
|---|---|
| A. 你本人真正理解区块链 | 能不靠背词，把一笔交易从钱包讲到最终确认 |
| B. 为「不确定」积累设计储备 | 每个关键决策都能放到对比矩阵里，而不是抄最近最火的链 |

## 1. 总原则

### 1.1 怎么学

每一课都走同一条路径：

```
直觉（ELI15）
  → 本科计算机定义
  → 协议工程师：状态机、攻击面、源码入口
  → 研究级：论文 / 形式化 / 数学（本轮不提前扔给你）
```

### 1.2 怎么研究项目

项目不是孤立景点。每条链都是「对同一组工程问题的不同答案」。

学完项目后，必须横过来按问题重排：

- 状态模型
- 共识
- 网络
- 执行
- Mempool
- 存储
- 密码学
- 账户与密钥生命周期
- 升级
- 经济安全
- 轻节点
- ZK
- 形式化验证
- 协议测试
- 失败案例

### 1.3 怎么服务「不确定」

「不确定」当前公开的技术主线是：**后量子结算**。

因此路线图不是「成为以太坊专家」，而是：

1. 先把任何一条链都共有的机器看懂
2. 再把「不确定」最可能直接采用的骨架看懂（尤其是 BFT + 应用/共识分离）
3. 再研究别人用性能、隐私、模块化换来了什么代价
4. 最后才决定「不确定」保留什么、放弃什么、什么值得重做

建议（不是事实）：

- 第一版「不确定」更应该像一台**可验证的结算机器**，而不是一台通用世界计算机。
- 不要为了创新而创新。先证明你理解了 Bitcoin 为什么能稳十几年，再谈独特能力。

## 2. 五层保证 + 六种混淆，必须从第一天分开

以后所有课都会反复使用这五层，外加六种常见混淆。先记住名字：

### 2.1 五层保证

| 层 | 问题 | 例子 |
|---|---|---|
| 密码学保证 | 数学假设还成立吗？ | 哈希抗碰撞、签名不可伪造 |
| 协议保证 | 诚实节点按规则跑，会不会分叉、会不会双花？ | +2/3 法定人数、最长链规则 |
| 实现保证 | 代码有没有忠实地实现协议？ | 两个客户端对同一区块算出同一状态根 |
| 部署保证 | 真实网络、真实时钟、真实磁盘会不会打破假设？ | 分区、断电、NTP 漂移 |
| 经济保证 | 破坏规则的人会不会亏到不敢做？ | 质押罚没、挖矿成本 |

### 2.2 六种不该混的东西

1. **协议安全 ≠ 实现安全**
2. **测试通过 ≠ 协议安全**
3. **TPS 高 ≠ 链更好**
4. **去中心化 ≠ 自动安全**
5. **有区块头 ≠ 有数据可用性**
6. **最终性（finality）≠ 交易已经广播**

Level 0 会把这些变成直觉。后面每个项目都要回来对这张表。

## 3. Level 0 → Level 10

每个 Level 的毕业标准写在右边。达不到，就不要进下一层。

| Level | 名称 | 优先级 | 毕业标准 |
|---|---|---|---|
| 0 | 区块链作为一台机器 | 必学 | 能画一笔转账的完整生命周期，并指出五层保证分别在哪失效 |
| 1 | 工程密码学入门 | 必学 | 能解释哈希、签名、Merkle 树各自挡住什么攻击，而不是只会写公式 |
| 2 | 状态模型 | 必学 | 能对比 UTXO / Account / Object / Resource，并说出并行性从哪里来 |
| 3 | Bitcoin 作为完整系统 | 必学 | 能解释为什么保守演进 + 全节点可验证，让它跑了十几年 |
| 4 | BFT 与 Cosmos/CometBFT | 必学 / 对「不确定」最关键 | 能讲清 Propose→Prevote→Precommit→Commit 为什么不能简化成「投票过 2/3」 |
| 5 | Ethereum：可编程与多客户端 | 重要 | 能解释账户、EVM、gas、PoS 终局，以及「多客户端如何仍保持确定性」 |
| 6 | 高吞吐架构 | 重要 | 能拆开 Solana / Sui / Aptos：协议、执行、网络、状态、硬件各贡献了什么 |
| 7 | 模块化、DA、共享安全 | 重要 | 能解释「有区块头 ≠ 有数据」，以及小链如何借用大链安全 |
| 8 | 隐私与简洁证明 | 进阶 | 能说明 Zcash 链知道什么/不知道什么，以及为何仍能防双花 |
| 9 | 横向系统：网络、存储、升级、经济、失败 | 重要 | 能从别人的事故里抽出可写成测试的 invariant |
| 10 | 「不确定」设计工作室 | 研究级 | 能对状态模型、共识、签名、升级给出带代价的决策矩阵 |

详细知识树见 [`01-knowledge-tree.md`](01-knowledge-tree.md)。

## 4. 两条平行轨道

从 Level 1 开始，学习永远走两条轨，不要只走一条。

```
轨道 A：课程（让你本人变强）
    Level 0 机器直觉
    Level 1 密码学工具
    Level 2 状态
    ...

轨道 B：案例（让设计有证据）
    先 Bitcoin
    再 CometBFT
    再 Ethereum
    然后才是高性能 / 模块化 / 隐私
```

轨道 B 的完整顺序和理由见 [`02-research-order.md`](02-research-order.md)。

另外还有一条**后量子轨**，从 Level 1 就埋点，但深度研究放在 Level 8–10：

```
轨道 C：Post-Quantum Blockchain Track
    先理解「签名是授权，不是身份本身」
    再理解 PQ 签名的体积 / 验签 / 网络代价
    最后才做算法敏捷、密钥轮换、紧急迁移手册
```

## 5. 每个 Level 内部怎么拆

统一拆四层，避免目录变成无序列表：

```
Level
 └─ Module      一个完整问题（例如：交易是什么）
     └─ Lesson  一节可学完的课
         └─ Knowledge Point  必须能用自己的话复述的点
```

依赖规则：

- 同一 Level 内，Module 按编号走。
- 跨 Level 的依赖写在知识树里。例如：没懂 Merkle 树，不准学 SPV；没懂 quorum intersection，不准学 Tendermint 锁规则。

## 6. 研究一条链时的固定模板

以后每条核心链都用同一份 19 节模板。第一轮**不填写全文**，只把模板钉死：

1. 一句话定义（禁止营销）

3. 架构图

5. 状态模型

7. 执行
8. 网络
9. 存储
10. 密码学 primitive
11. 安全假设

## 7. 算力用在哪

文章可以再写。算力不要浪费在重复生成说明文。

优先顺序：

1. 签名与验签 benchmark（尤其后量子）
2. 数据库崩溃 / 原子提交实验
3. 共识不变式的 property test / fuzz
4. 多实现差分测试
5. 网络分区与拜占庭节点仿真
6. 形式化模型（TLA+ 等）——放在你会读状态机之后

每次实验必须留下：输入、环境、版本、随机种子、结果、反例、修复、regression test。

第一轮不做实验。Level 0 先把「什么叫反例、什么叫 invariant」变成口语。

## 8. 第一轮之后你会有什么

读完本文件 + 知识树 + 研究顺序 + Level 0 之后，你应该能够：

1. 用「复制状态机」而不是「分布式数据库」来称呼一条链
2. 把「我点击了发送」和「链已经最终确认」分开
3. 指出双花、假余额、假确认分别破坏了哪一层保证
4. 知道下一层为什么必须先学哈希和签名
5. 知道为什么我们先研究 Bitcoin，而不是先研究最快的链

你还不应该：

- 选择「不确定」的共识算法
- 选择状态模型
- 实现一条链
- 判断 Solana / Sui / Ethereum 谁更先进

那是后面 Level 的工作。
