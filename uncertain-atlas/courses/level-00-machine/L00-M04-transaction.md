# L0.4 交易

优先级：必学

## A. 先修知识

状态会变。变之前必须有授权。  
本课把「那张申请单」单独拿出来看。

---

## B. 核心问题

**交易究竟是什么对象？为什么不能把它理解成「转账按钮」？**

---

## C. 直觉（ELI15）

交易更像一张**已经签字的支票**，不像一次银行柜面操作。

支票上写着：从哪出、到哪去、多少、以及防别人拿去再兑一次的信息。  
你签字之后，这张纸自己就是请求。银行柜员（节点）只能：

- 收，按规则入账
- 拒，因为余额不够、签字不对、已经兑过
- 暂时放抽屉里（mempool），还没轮到它

柜员不能因为喜欢你，就替你改收款人。  
你点了钱包上的按钮，只是**制造并寄出**这张支票。寄出 ≠ 入账。

三种完全不同的状态：

```text
有效（valid）     ：按当前规则，这张支票格式对、签字对、此刻花得起
已打包（included）：某个区块把它写进去了
最终（final）     ：按该链的最终性规则，再改已经极难或不可能
```

钱包爱把三者涂成同一个绿色对勾。你不要跟着涂。

---

## D. 正式定义（本科计算机）

**交易（transaction）**：对状态转移函数的一份字节串请求，通常包含：

1. 意图：转多少、调什么、写什么
2. 授权：签名或花费证明
3. 防重放：nonce、UTXO 指针、过期高度、chain id 等
4. 资源预算：手续费、gas limit 等

**有效性（validity）**：`Apply(S, T)` 不拒绝。有效性依赖**当前状态**。一笔刚才有效的交易，可能因为别人先花了同一笔钱而变成无效。

**重放（replay）**：同一份已授权字节串被再次接受为一次新的有效转移。

防重放的常见方法（先认脸，细节后面）：

| 家族 | 方法 | 直觉 |
|---|---|---|
| 账户模型 | nonce 递增 | 每张支票有序号，用过的号作废 |
| UTXO | 花费具体输出 | 那张「币」用完就没了 |
| 跨链 | chain id / 域分离 | 这条链的支票不能拿到邻县兑 |

**事实：** 交易是数据，不是过程。过程是节点如何检查、排序、执行、落盘。

## E. 最小案例

阿安签了：

```text
T = { from: A, to: B, amount: 4, nonce: 7, chain: Uncertain, sig }
```

时间线：

1. 阿安本地构造并签名。此时链上状态没变。
2. 广播。部分节点放进 mempool。仍没变。
3. 出块者把 T 放进高度 100 的块。执行后 A 少 4，B 多 4，nonce 变成 8。
4. 若该链是概率最终性，高度 100 之后仍可能被另一条更重的链替换。T 可能「曾经入账又被抹掉」。
5. 阿安把同一份 T 再发一次。诚实节点应因 nonce 或 UTXO 已花而拒绝。

另开一个陷阱：

```text
T2 金额改成 9，但重复使用给 T 的签名
```

验签应失败，因为签字绑的是原来的消息。  
若实现只验「有个签名」而不绑消息，授权体系崩溃。

## F. 真实项目

- **Bitcoin（事实）**：交易指明输入（哪几个 UTXO）和输出。没有账户 nonce。重放防护主要来自「那个输出只能花一次」。
- **Ethereum（事实）**：交易有 nonce、gas、chain id（EIP-155 就是为了跨链重放）。类型后来变成 0/1/2 等。
- **Solana（事实）**：交易必须列出将碰到的账户。这既是安全边界，也是并行的前提。Level 6 再讲。
- **「不确定」（建议）**：先把「什么字段进入签名、什么算同一笔」写成不能含糊的规范，再加功能。

## G. 源码

预告，不是作业：

1. 交易反序列化 / 规范编码（非 canonical 编码是经典分裂源）
2. 验签
3. nonce 或 UTXO 花费检查
4. 费用是否足够进入 mempool（这是策略，不一定是共识）

注意：mempool 拒绝 ≠ 共识上永远非法。这是后边反模式课会反复打的点。

---

## H. 攻击者视角

1. 重放旧交易。
2. 把交易改几个不影响签名的可 malleable 字节，让交易 ID 变了但语义还在（Bitcoin 早期的 transaction malleability）。
3. 发海量「验签很贵但最终无效」的垃圾，打 CPU（后量子时代更危险）。
4. 诱骗钱包签下一笔用户没看懂的交易。

---

## I. Trade-off

| 选择 | 得到 | 失去 |
|---|---|---|
| 交易字段很少 | 好验证、好证明 | 应用表达力弱 |
| 交易能带任意程序 | 灵活 | 必须有资源计量，否则无限循环 |
| 把很多检查放进 mempool 策略 | 节点能自我保护 | 两个节点策略不同，用户会以为「链拒绝了」 |

---

## J. 对「不确定」的意义

后量子签名体积大、验签贵。交易设计会直接影响：

- 区块能装多少笔
- mempool 会不会被验签打爆
- 轻节点要带多少字节才能证明「这是一笔合法授权」

这些是工程问题，不是算法比赛。Level 1 和 Level 10 会回来。
