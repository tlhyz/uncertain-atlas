## 一句话

**《全球区块链架构图谱》+《不确定链设计参考库》**

## 两个同等重要的目的

| 编号 | 目的 | 失败长什么样 |
|---|---|---|
| A | 用户本人真正理解区块链 | 会背名词，讲不清一笔交易从钱包到最终确认 |
| B | 为「不确定」积累设计储备 | 还没比较就抄最近最火的链 |

不要为了创新而创新。  
也不要为了成熟而照抄。

最终问题永远是：

> 这个设计是否真的适合「不确定」？

## 质量铁律（写完必须对照）

视为失败的输出：

1. 堆术语，没有因果关系
2. 照抄官网营销稿
3. 只讲优点
4. 只讲理论，不看实现
5. 只看代码，不问为什么这样设计
6. 只看现在，不看历史演化
7. 把 benchmark / 官网 TPS 当事实
8. 把 TPS 当唯一指标
9. 把测试通过当成协议安全
10. 混用：协议保证 / 实现保证 / 部署保证 / 经济假设 / 密码假设

每条重要判断必须标明：

- **事实**
- **推断**
- **建议**

资料优先级：

1. 正式协议规范
2. 官方源码
3. 正式论文
4. 官方技术文档
5. EIP / BIP / RFC / ZIP
6. 安全审计
7. Postmortem
8. 核心开发者技术讨论
9. 高质量第三方研究
10. 普通博客

## 教学铁律

路径必须是：

```
直觉 ELI15
  → 本科计算机
  → 协议工程师（状态机 / 攻击面 / 源码入口）
  → 研究级（论文 / 形式化 / 数学）
```

不要一开始把第四层扔给用户。

每课必须包含：

A. 先修知识  
B. 核心问题  
C. 直觉  
D. 正式定义  
E. 最小案例  
F. 真实项目  
G. 源码入口（适合时）  
H. 攻击者视角  
I. Trade-off  
J. 对「不确定」的意义  
K. 五道测试题（先不给答案，等用户回答再批改）

## 「不确定」主线（建议，不是事实）

当前最明确的技术方向：后量子结算。

因此优先顺序是：

1. 先看懂任何链都共有的机器
2. 再看懂更可能采用的骨架（BFT + 应用/共识分离）
3. 再研究别人用性能、隐私、模块化换来的代价
4. 最后才决定保留、放弃、重做

第一版更应该像一台可验证的结算机器，而不是一台通用世界计算机。
